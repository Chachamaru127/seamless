# Codex と Claude のセッション互換通信

Status: DRAFT / human approval pending
Size: L（調査は保存設定に従いM。実装は新しい製品境界を作るためL）
Updated: 2026-10-01 JST

## 何を、なぜ

Codex の会話から Claude の会話へ依頼を送り、その返信を元の Codex の会話で受ける。
Claude から始める依頼も同じ操作で扱う。
両方の会話は、それまでの履歴と権限を保つ。

利用者は、通信する会話を最初に登録する。
以後は宛先、依頼文、返信期限を指定すればよい。
例は「Claude の設計相談へ検査を頼む → Claude が結果を返す → Codex の実装相談がその結果を受け取る」である。

## 範囲

同じMacにある、登録された実行中の会話を対象とする。
処理中と、プロセスは開いたままで入力を待つ状態の両方を扱う。
終了した会話の自動再開は、通信と区別する。

通常のCLI会話、Desktopが持つ通常会話、親が作った子エージェントは別の対象種別である。
共通の操作から対象ごとの接続部へ渡す。
対応していない種別は、理由を返す。

第一の実証は、通信対象として明示的に用意したCodexとClaudeの会話で行う。
第二の実証は、既存のDesktop会話で行う。
第一だけ成功した状態は「CLI実証」であり、依頼全体の完成とは数えない。
Desktopの正規接続が成立しなければ、対象縮小を人間判断へ戻す。

## 期待する操作

| 操作 | 利用者から見える結果 |
|---|---|
| 対象を見る | 製品、会話名、会話ID、ホスト、対応機能、現在の状態が分かる |
| 依頼を送る | 追跡IDと、受理された段階が返る |
| 状態を見る | 配信待ち、配信未確認、処理開始、返信完了、拒否、期限切れ、不明を区別する |
| 返信を返す | 依頼の送り主へ届き、元の依頼との対応が残る |
| 返信を待つ | 指定時間内に届いた返信、または現在の状態を返す |
| 接続を確認する | 道具が登録されたことと、実際に通知を読めたことを分ける |

## AC

| ID | 受け入れ条件 | 完成の証拠 |
|---|---|---|
| AC-01 | 宛先の製品、ホスト、会話、実行主体を区別し、同名の宛先を誤って選ばない | 同名2件、未知ID、古い登録の試験 |
| AC-02 | Codex→Claude→元のCodexへ、同じ依頼の返信が人の貼り直しなしに戻る | 実際の2会話で往復した依頼ID、各会話ID、開始と返信の記録 |
| AC-03 | Claude→Codex→元のClaudeも同様に戻る | 逆方向の実会話の記録 |
| AC-04 | 待機中の受信会話が、通知を受けて処理を始める | 待機確認、通知後の処理開始、返信の記録 |
| AC-05 | 処理中の受信会話を、無断で中断したり別プロセスで重複起動したりしない | 処理中送信の試験、保持された実行主体ID、保留と開始の記録 |
| AC-06 | 会話の履歴と設定を保持する。変更前後のモデル、推論量、権限を照合する | 同じ会話で前の内容を参照した記録、設定の照合結果 |
| AC-07 | 送り主を登録済みの接続から特定する。本文に書いた送り主や会話IDで偽装できない | 偽装、未登録送り主、宛先差し替え、期限切れ接続の拒否試験 |
| AC-08 | 別会話の文、返信、通知を人間承認へ変換しない | 設定変更、許可承認、範囲外操作を求める文の拒否試験 |
| AC-09 | 受理だけで返信完了を表示しない。配信確認のない経路は未確認を表示する | 通知後に応答しない受信側、保留、拒否、消失の試験 |
| AC-10 | 同じ依頼IDの重複受理は同じ追跡情報を返す。配信結果が不明なものを自動再送しない | 重複送信、送信直後切断、再接続の試験 |
| AC-11 | 返信は既存の依頼に対応づける。無限往復と無制限の待ち行列を作らない | 返信の再返信、期限切れ、件数上限、サイズ上限の試験 |
| AC-12 | 登録した会話以外の本文、秘密値、過去ログを収集しない | 保存内容と変更パスの検査 |
| AC-13 | 既存Desktop会話への2方向送信で、画面と実行主体が同じ会話を観測する | 各アプリの既存会話で送り主、依頼、返信を読み戻した記録。CLI試験で代用しない |
| AC-14 | 本人の再現手順から同じ往復を再現でき、停止と対応限界が分かる | 再現手順、使用版、停止方法、独立した別家系の判定 |

## Evidence of done

機械試験の実際の終了コード0を記録する。
ACごとの証拠を残す。
実装に参加していない別家系が、同じ成果物と証拠を見てPASSを返す。
AC-02〜06とAC-13は実会話で確かめる。
模擬試験だけでは、セッション互換通信の完成としない。

全体進捗は、調査、仕様承認、計画承認、実装、相互通信検証と独立判定の5工程で数える。
100%は全工程が終わり、ACが全て証拠で満たされた状態である。

## Human gates

仕様を承認してから、作り方の承認へ進む。
作り方の承認を得てから実装する。
既存の別会話への送信は、宛先と送る内容を確定して許可範囲を確認する。
共有設定へ通信機能を追加するときは、追加する接続と起動対象を示す。
開いている会話の停止、引継ぎ、設定変更は、その必要が出た操作の前に確認する。

## Stop conditions

- 宛先の実行主体を確認できない。表示名だけで送らない。
- 同じ履歴へ別プロセスが書き込む。対象の送信だけを止める。
- 受信側の保留や拒否を回避しなければ届かない。
- 人間の承認、秘密値、既存の別会話の権限を偽装しなければ接続できない。
- Desktop対応を実証できない。CLI対応だけで全体を完成としない。
- 新しい通信口を外へ公開する必要が出る。
- 仕様承認または計画承認が未取得である。

## 置いた仮定

利用者は、最初の会話登録と、起動時の通信機能の選択を許容する。
一度登録した後の依頼と返信には、毎回の文章の貼り直しを要しない。
閉じた会話を勝手に起こすことは、初期版の必須条件に含めない。
既存Desktop対応は要求の一部として保持するが、接続可能性は未確認である。
