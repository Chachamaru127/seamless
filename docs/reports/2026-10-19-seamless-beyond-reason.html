seamless / team-research（L）2026-10-19 JST
Reason を超える設計

seamless を Reason より上にする。
どこで勝ち、どこを追わないか。

Reason Network は「自分の網」を作る製品です。seamless は、あなたがもう持っている網（Claude Code の公式メッセージ口、Codex の codex queue、Grok Bot の webhook、SSH）を束ねる配線にします。自前の名簿、鍵、中継、常駐、本文の保存を持ちません。届いたかは、相手の記録を読んでから言います。

ひとことで。 同じ土俵（チームの網、10 製品）では超えられません。超えるのは 4 つの軸です。届いたの正確さ、持たないもの（常駐 0、本文 0、外部接続 0）、入口から初回往復までの速さ、身元と失効を自前で作らない。この 4 つで勝ち、総合点ではセキュリティで並びます。

01 今日分かった大きな事実（前提が変わった）

調べ直して、計画 v2 の前提が 2 つ古いと分かりました。

事実意味出典
Claude Code は 2026-08 から公式に「セッション同士のメッセージ」を持つ。 同じ Mac では会話ごとの socket（=同じ Mac の中だけで通じる口）。socket の場所はフック用の環境変数 CLAUDE_CODE_MESSAGING_SOCKET として公開され、「スクリプトから投稿したいとき」の節がある。 seamless が今使っている Claude の口は、もう「内部 API」ではなく「文書化された挙動」。Reason の Claude への押し込みも同じ口。 code.claude.com/docs/en/cross-session-messaging
Codex CLI 0.163.0 に codex queue --thread <ID> --message がある。 ただし「保存した」時点で成功を返す。読まれたかは分からない。Desktop の /goal 中は消費されず手動 Steer が要る（issue #52705、open）。返事を読む公式手段の要望（#54252）は未回答。 書く口は公式。「届いた」を確かめる口は無い。ここが seamless の差別化になる。 手元で codex queue --help 実行。github.com/openai/codex/issues/52705、54252
Reason のエンジンは reason-network CLI まで OSS で、アカウントなしの team link モードがある。 非公開なのは製品の reason CLI。 「アカウント不要」「OSS」は seamless だけの売りではない。前回の説明を訂正。 github.com/reason-machines/reason-network README
Claude Code Channels は research preview。 自作の channel は対話セッションでしか読み込めず（-p では無視）、通知に受領確認が無い。忙しいときは次のターンにまとめて届く。 v2 が主経路にした Channels は、補助（CI や外部イベント用）に回す。 code.claude.com/docs/en/channels-reference
Reason の「届いた」は受信側デーモンの ack（stored / delivered / held）。 「bypass の Claude が hold しているのに delivered と言った」issue #24 は 10-18 に修正。「delivered」が「読んだ」を意味するかは未定義。 seamless は「相手の記録に依頼 ID が現れるまで届いたと言わない」で、この穴を設計で塞ぐ。 DESIGN.md、issues #24

02 どこで勝つか（4 つの軸と、測り方）

軸何を測るかseamless v3 の目標Reason の今
届いたの正確さhold、busy、/goal 中に「届いた」と誤表示した件数0 件。相手の記録で依頼 ID を見るまで「預かり」デーモンの ack。#24 で誤表示があり修正済み
持たないもの追加プロセス数、本文の保存バイト数、ローカル往復で接続する外部ホスト数0、0、0デーモン 1、SQLite に本文、既定で n0 の中継
入口から初回往復一覧が出るまでの秒数、1 往復の操作回数、質問数10 秒、3 操作、0 問install + setup + ログイン（または team 作成）+ エージェント再起動
身元と失効自前の鍵と名簿の有無、失効が機械的に効くかOS ユーザーだけ。自前の鍵と名簿を作らない（オンライン機能は持たない。2026-10-19 判断）自前の署名つき名簿。除名は「暗号的に無力にはならない（this is for friends）」
追わない軸。 対応製品数（Reason は 10）、他人のマシンを含むチーム名簿、オフラインの郵便箱、LAN と P2P、遠隔の承認ポップアップ。ここは Reason の本体で、1 人では追えません。README に「チームなら Reason。同じ会話に両方をつながない」と書きます。

03 仕組み（実際には何が動くか）

1. 探すClaude は /tmp/cc-socks-<uid> と sessions の記録。Codex は rollout と所有者照会。Grok Bot は本人の名簿。常駐なし。
2. 送るClaude は公式 socket。Codex は codex queue。opencode は plugin。Grok Bot は webhook（HTTPS）。遠隔は持たない。
3. 確かめる相手の記録を読む。依頼 ID が見える → 渡った。ターンが始まる → 処理中。replyTo が一致 → 返事。
4. 残す~/.seamless/reservations/ に hash、状態、時刻だけ。本文は残さない。二重には送らない。

状態の言葉は 5 つ。 預かり / 渡った / 処理中 / 返事 / 不明。新しく、「相手が承認待ち（hold）」と「Codex が手動 Steer 待ち」を区別して出します。socket への書き込みが成功しても、相手の記録に現れなければ「渡った」と言いません。

遠隔（旧案、取り下げ）は SSH。 seamless key issue --scope read,send --host mac2 が、command="seamless inbound --scope read,send",no-pty,… の authorized_keys 行を出します。身元は SSH 鍵、暗号化は SSH、失効は行の削除。自前の暗号と NAT 越えを作りません。Tailscale の上でも同じです。代わりに、相手の Mac が起きていなければ「不明」で止まります（郵便箱を持たない）。

05 応援の答え（採用、見送り、要確認）

Codex gpt-6.1-sol（逆家系。一次資料と web 検索。chatgpt-2 契約）

  • 採用 「公式経路への移行は保守性に効くが、Reason も同じ公式経路を使うので速さの優位は断定できない」。
  • 採用 「Channels は受領確認がなく黙って落ちる。返信ツールでの相関が要る」。
  • 採用 「codex queue は登録と消費が別。CLI の終了 0 を到達にできない」。
  • 採用 「A2A は既存 CLI 会話へ注入する口ではない。アダプタは残る」。
  • 採用 優先案 1（配送証拠を ID で照合）、2（今の画面から依頼と返信確認）、4（閲覧、送信、起動、承認の分離）。
  • 採用 「Reason の『CLI 非公開』は製品 CLI の話。エンジンにも CLI がある」。前回の説明を訂正。
  • 見送り 優先案 5「Reason との橋渡しで獲得」。需要が未検証で、二重配送と権限の変換が危ない。v1 は「併用の注意」まで。

Grok 4.7（X 調査。required）

  • 採用 乗り換えの決め手は「画面操作とコピペをやめる」「同僚の枝（repo、branch）が見える」「公開エンジン」。しょうへい氏は Computer Use の遅さから乗り換え（X、2026-10-16）。焼山氏は「同じフォルダへ数秒で push、8 秒」（X、2026-10-19。1 人の 1 計測）。
  • 採用 「受理をツール許可にするな」（hexablob 氏、X、2026-10-18）。seamless の不変条件 3 と一致。
  • 採用 agmsg 作者は「公式モニターが 30 分で切れるため socket と queue を選んだ」（X、2026-10-15）。主経路の判断と一致。

類似製品が定着しなかった理由（出典つき）

  • agmsg（Claude と Codex の会話ツール）は 3 週間で手打ち 9 回、会話 1 件、7 週間後にアンインストール。「人間が手で起動するツールは死に、走っている中から呼べるものが生きた」（zenn.dev/kaz_hira、2026-10-03）。→ seamless は「今開いている会話の中から 1 行」を守る。
  • agmsg の運用で 3 分ごとに Codex を起動し、3 時間で約 60 会話、メモリ不足（fujibee/agmsg #163、2026-06-19）。→ 空振り起動をしない（不変条件 2）。
  • Codex の /goal 中は外部 queue が待ち続け、手動 Steer が要る（openai/codex #52705）。→ 公式入口でも「受理 ≠ 読んだ」。証拠が要る。

何を決めるか

2. Codex Desktop の内部 IPC を読み取りに使い続けるか

何を決めるか
Desktop の会話の「届いた」判定に、内部 IPC（アプリ同士が話す非公開の口）を使い続けるか。CLI の会話だけを正式対応にするか。
推奨
決定（2026-10-19）: 使い続ける。「Desktop は未確認」表示を許容し、公式の読取り口（openai/codex #54252）が出たら乗り換える。
許可すると何が起きるか
Codex Desktop の会話が一覧に残る。版ごとの互換表の更新が続く。
今回はしないこと
Desktop の IPC を公開物の「主経路」と名乗ること。
後から戻せるか
戻せる。CLI 限定への切り替えは設定 1 つ。

3. 比較実測のために Reason Network を入れるか

何を決めるか
週 7〜8 の 5 指標の実測のために、Reason Network をこの Mac（または別の OS ユーザー）に入れるか。
推奨
入れる。同じ OS ユーザーでよい（同じエージェント、同じ版で測るのが公平）。条件は 2 つ。Reason の setup が書き換える各エージェントの設定ファイルの backup を先に確認する。同じ会話に seamless と両方をつながず、計測は順番に行う。終わったら reason-network leave → setup --remove で消す。
許可すると何が起きるか
外部ソフトの導入。各エージェントの設定ファイルに Reason のフックが書かれる（backup つき）。n0 の公開中継に接続する。
今回はしないこと
Reason のワークスペース作成、他人の招待。
後から戻せるか
戻せる。手順は README に記載。設定ファイルの backup を確認してから進める。

決定済み（2026-10-19）: オンライン機能は持たない（H4）。GitHub Issues #1〜#20 と 30 分ループで実装（H7。施工は DeepSeek 1017）。計画の書類は specs/2026-10-universal-wiring/（spec、Plans、tasks、evidence）。残る判断: 名前と配布（H5）、規約（H6）、Antigravity の実行ファイルの場所（未決 3）。

08 進捗

プロジェクトの目的: 立花さんが、今開いている AI にそのまま一言を届け、届いたかを正直に知ることができる配線アプリ seamless を OSS として出す。

全体進捗: 調査は 100%。設計案は約 90%（本人の 3 判断が残る）。実装、実測、公開は 0%。100% の定義は「v1 が公開され、第三者が説明どおりに動かし、issue を出せる状態」。

今やっている作業: 一次資料と応援 2 つの答えを突き合わせ、勝つ軸を 4 つに絞り、計画 v3 と採点を書いた。Grok の答えも反映した。

何のためにやるのか: 「Reason と同じものを作って負ける」を避け、1 人で保守できる範囲で Reason に勝てる軸を決めるため。
