## 方針

1. 既存の単一 write 経路（delivery）と観測器を土台にする。新しい受信箱、DB、常駐プロセスを作らない。
2. 相手の一覧は、毎回の観測で作る。保存する名簿を持たない。制限の設定だけをファイルに置く。
3. 呼ぶ側は、道具のプロセスの親をたどって実観測で特定する。`--caller` 引数は使わない。
4. 状態は保存しない。照会のたびに元の会話を読み直して段階を決める。
5. 版と接続方式の判定は「対応の組」の表1つに集める。読み書きの入口で必ず通す。
6. 普段の画面への常設と UI は、手元の実装と試験が通ってから、Human gates の承認で入れる。

## 決定の反映（2026-10-03 立花さん）

- 名簿による登録をやめ、このMacで動いている会話を自動で見つけて、読む、送るを初めから許す。制限は任意の設定（4つ目の道具とコマンド）で行う。
- 既定の探す範囲は同じ作業場所。
- 同じ製品の組を範囲に入れる。
- 製品は道を作り、運用は縛らない。製品が守るのは「claudex のコード自身は、相手の文を理由に設定を変えない」こと（AC28）と、呼ぶ側を実観測で特定すること（AC3）。

## 主な作り方

### A 自動でつなぐ
- 呼ぶ側の特定: Claude は道具のプロセスの親プロセスを `~/.claude/sessions/*.json` の pid と照合する。Codex は、Codex 本体が道具の呼出しごとに付ける `_meta["x-codex-turn-metadata"]` の `session_id`（子エージェントは `thread_id`）で特定する（Codex 同梱の道具と同じ方法。T1b で利用者の道具にも付くことを実測）。付いていなければ止める。Codex をコマンド経由（`CODEX_THREAD_ID`）で呼ぶ側とする経路は持たない（2026-10-03 決定）。補助として、道具のプロセスの親が Codex の app-server であることと、作業場所の一致を照合する。
- 一覧: Claude は `~/.claude/sessions/*.json`、Codex は Desktop の owner 照会と rollout のファイル名から作る。今の Codex の観測は snapshot（本文を含む）を受け取るので、一覧には使わない。本文に触れずに cwd を得る経路（rollout の先頭のメタ情報行だけを読む、など）を実証し、できなければ Codex の作業場所は「未確認」にする。
- 制限の設定: `~/.claudex/limits.json`（mode 0600、symlink 不可）。書込みは `limits.ts` だけが行う。プロセスをまたぐ排他（ロックファイル）の中で、再読込み、hash 照合、一時ファイルへの書込み、rename を行う。設定なしは制限なし。壊れている、読めないときは止める。
- 道具: sessions、read、send に、制限の設定を扱う4つ目の道具を足す。同じ内容をコマンドでも出す。
- 既存の名簿（`--registry`）は、移行の間だけ読み、「除外」と「範囲」へ変換する手順を用意する。

### B 再開と世代
- Codex の世代は owner の clientId、Claude の世代は pid と起動時刻。会話 ID は Codex は thread ID、Claude は sessionId。Claude は Desktop の再開で sessionId ごと変わる（観測記録）。
- 一覧で、同じ作業場所に「直前に止まった会話」と「新しく現れた会話」があれば、ID の変化の候補として並べて表示する。同じ会話と断定しない。
- 除外の設定は、作業場所と製品で書く形を勧め、会話 ID の除外は ID が変われば切れて一覧に表示する（spec Open decision 2 の案）。
- 今の delivery は送る瞬間に宛先を選び直す。一覧で選んだ宛先（会話 ID、世代、作業場所）を固定した選択票を send に渡し、書込み直前の照合にもその票を使う。
- 世代や ID の変化を表示するため、最後に見た識別情報（製品、会話 ID、世代、作業場所、時刻。本文なし）を `~/.claudex/seen.json` に24時間だけ置く。比べる相手がなければ「変化は未確認」と出す。

### C 対応の組
- 対応表は構造化した正本1つ（`compat.ts`）から、人向けの `compat.md` を生成する。通常利用は状態が「確認済み」の組だけ。
- 試験用ペアの確認経路は、CLI の明示した引数と、試験用の制限の設定（試験用ペア以外を除外）だけで動く。通常の名簿では動かない。
- 試験用の組が「立花さんの指定した組」であることは、コードではなく承認 G1 の手続きで担保する。コードが担保するのは、既定の設定では通らないこと、`--target` で呼ぶ側と指定の1件だけに絞ること、読取りだけで送信と設定の変更ができないこと（2026-10-04 段 B・C の判定の中2）。

### D 状態と待機
- 段階は、受理 = delivery の受理、到達 = 相手の記録に依頼 ID がある、処理開始 = 相手の記録で依頼の後に応答が始まった、返答完了 = replyTo が一致する返事がある。
- 処理開始の観測方法は、製品ごとに試して決める（Open questions 2）。
- 照会は send の送り主だけ。相手の記録を読むときは read の許可を確かめる。許可のない ID は「該当なし」と同じ応答を返す。
- 止めるのは、不明になった依頼と同じ依頼を別の ID で自動再送すること（spec AC12）。独立した新しい依頼は止めない。「同じ依頼」は、送り主、宛先、replyTo、本文の鍵付き hash がすべて同じで、前の依頼が「不明」のまま24時間以内のもの。予約は今の送り主と依頼 ID の単位に加え、この条件の単位でも取る。鍵は `~/.claudex/key`（mode 0600）に置き、再起動後も同じ鍵を使う。
- 処理開始の根拠（T13a で実測）: Codex は依頼の入った turn に依頼より後ろの項目があること、Claude は parentUuid をたどって依頼の記録に戻れる assistant 記録があること。処理開始は、依頼 ID と対応付けた根拠があるときだけ出す。対応付けできない応答の開始は根拠にしない。段階を作業の進み具合（25%、50% など）にしない。

### E 安全
- 固定の試験文を3経路で送り、許可、承認待ち、設定ファイルの hash が変わらないことを確かめる。

### F 常設
- wire.sh の MCP 登録表に claudex を1件足す。`plan` で差分を見せ、`apply`、`check` の順に進める。外すときは同じ登録表から消して `apply`。
- 登録表の実体 `~/.claude.json` は Grok も自動で読む。共有の登録表へは入れず、Claude と Codex だけへ配る経路を wire.sh に設計してから入れる。確かめ方は、Grok が実際に読み込んだ道具の一覧に claudex が無いこと。
- 各アプリの設定ファイルを直接書かない。

## 施工の体制（2026-10-03 立花さん指示）

- 判断の要らない大量の実装作業は、Codex Astra（推論量 low、ultrafast）に任せる。
- 小分けにせず、段ごとなど大きなまとまりで1回に依頼する。依頼文には対象のタスク ID、Done when、触るパス、試験のコマンド、止める条件をまとめて書く。
- 判断が要る作業（呼ぶ側の特定の実測、設計の分岐、承認が要る操作）はリーダーが持つ。
- 完了の判定は施工した側ではなく、verify.sh の実終了コードと逆の家系の判定で行う。ultrafast の指定方法は、依頼の前に Codex CLI の実際のオプションで確かめる。

## Open questions

1. Codex で呼ぶ側を特定する方法は、T1 の実測で決める（spec Open decision 1）。
2. 「処理開始」を製品ごとに何で観測するか。依頼 ID と対応付けられる根拠を実測で探す（T13a）。見つからない製品では処理開始を常に「未確認」にする。
3. 段 H の Codex 側。Codex の回答（2026-10-03）: 同梱のコードに会話の入口と UI の仕組みはあるが、今のアカウントで任意の UI を表示できるかは未検証。最小の検証は、手元のプラグインで読取り専用の状態を会話1つに出すこと。
4. 制限の設定と予約に残る項目（storage.md）。予約の hash は本文を含むため、鍵を付けて総当たりで戻せないようにする。
6. 返信の `invalid_reply`（2026-10-03 観測）: 依頼を受けた直後に replyTo 付きで返すと、元の依頼がまだ読めず、書込み前に拒否される。Codex は依頼の記録が現れてから同じ ID で呼び直して通した。待って再照合するか、理由を分けて返すかを段 D（T18）で決める。
5. busy 中の Codex 会話への `thread-follower-start-turn` が、動いている turn を中断するか。T28 の前に試験用ペアで確かめる。
