00

30秒でわかる結論

01
Reason は「別の商品」で、正面から戦う相手ではない。

Reason は複数人、複数マシンのための網。seamless は1台、1人のための配線。Reason を基準にすると、チーム機能で0.42点、対応相手で0.18点、最初から負ける。この0.60点は、機能を足しても埋まらない。設計思想が違う。

02
統合の利得は +0.6点。その大半は「Grok Bot の玄関口まで届く」ことに集中している。

内訳は、外部の入口 +0.20、配送 +0.14、導入 +0.14、対応相手 +0.06、チーム +0.06、OSS +0.03。相手探索、証拠、安全はほとんど変わらない。つまり、統合の是非は「Grok Bot の玄関口まで公開物に含めるか」とほぼ同じ。

03
リリースの障害は、機能ではなく配布にある。

ライセンスがない。npm の seamless は取得済み。Grok Bot 側は /usr/local/bin/python3 固定で、Apple Silicon の標準環境では動かない。CI は Keychain を読む検査を外せない。README は旧方式のまま。互換表は10月2日で止まっている。ここを閉じないと、OSS（誰でも見て使える公開ソフト）として出しても「動かない」で終わる。

このレビューの立場

統合そのものは正しい。botress は「Grok Bot 専用ツール」というブランド問題を抱えていて、単独で OSS にする理由が弱い。seamless の一機能にすると、予約、再送禁止、4段階の証拠に乗る。ただし、repo ごと抱えるのではなく、能力を分けて迎えるのが安全で、説明も短くなる。v0.1 は既存の webhook 方式まで。玄関口（gateway）は法務確認後の任意アダプタにする。

02

競合の正体

Reason が強いのは、機能数ではない。「最初の10分」と「チームの文脈」を、製品として閉じているからだ。

「誰もやっていないのは、文脈つきの生きたセッションのチーム名簿だ。人、マシン、エージェント、リポジトリ、ブランチ、busy/idle、いま何をしているか。だからエージェントは、当てずっぽうに配信するのではなく、正しい相手を選べる。メッセージ送信は簡単な部分にすぎない。」 Reason Network DESIGN.md（2026-10-19 取得、要旨訳）

強い理由

＋
導入が1行で終わる

curl … | bash のあと reason network setup。10以上のエージェントを検出して、MCPとフックを書く。利用者はほとんど何も設定しない。

＋
チームの文脈が最初からある

人 → マシン → セッションの階層。repo（コードの保管場所）@branch（作業の枝）、busy/idle（作業中/待機中）、doing（いま何をしているか）まで出る。誰に頼むかを、勘で決めなくていい。

＋
届き方が速い

Claude Code、Codex、opencode、Pi、Reason はセッションの途中に届き、待機中なら起こす。同じLANなら直結。1.5〜2秒で返る、と公式が書いている。

＋
チームの衝突を避ける設計

同じrepoで誰が動いているかが見える。オフラインの相手には郵便箱が1日預かる。hold（保留）/ refuse（拒否）、loop guard（AI同士の無限往復を止める仕組み）、ask_user（本人にポップアップで承認を取る道具）まである。

＋
公開と勢いがある

エンジンは MIT または Apache-2.0。公開から3日で 432 stars / 31 forks。v0.10.7 が 2026-10-18 に出ている。コミュニティと会社が後ろにいる。

弱い理由（＝seamless の余地）

−
チーム前提で、重い

1人で使うにも「チーム」と「招待」の概念を通る。デーモン、常駐サービス、自動更新、メニューバー。壊れたときの切り分けが、seamless より多い。

−
専用CLIは非OSS

エンジンだけが公開で、実際に使う reason CLI は proprietary（非公開の専用ソフト）。OSS の気軽さと、製品の都合が一致しない部分がある。

−
コーディングエージェント中心

日常のアシスタント（Grok Bot、Muse、Dot、LINE）は、あくまでコーディング網への入口。Grok Bot は Reason MCP 経由で参加する。アカウント無しの経路で使えるかは、資料からは確定できない（未確認）。

−
まだ若い

公開から3日、42コミット。M4（チーム機能）は未着手。仕様と配布がこれから動く。長く使う前提だと、更新の荒波を浴びる。

−
「届いた証拠」は、seamless ほど厳密ではない

ack と receipt はあるが、seamless の「同じIDは再送しない」「不明なら送らない」「受理と会話項目と echo ID の3点照合」ほど、送信の重複と誤認に神経質ではない。

大事な線引き

Reason を買う人は「チームで、複数マシンで、なるべく設定せずに使いたい人」。seamless を買う人は「1台で、静かに、自分の会話だけをつなぎたい人」。同じ棚に並ぶ商品ではない。比較採点は、負けを宣告するためではなく、どこで戦わないかを決めるために使う。

04

統合プランの精査

良い点と危ない点を分ける。統合の価値は「Grok Bot に届くこと」に集中していて、それ以外は配布の整備で上がる。

良い点

＋
設定と入口が1つになる

~/.seamless、MCP 1本、CLI 1本。利用者は「seamless を使う」とだけ覚えればよい。botress と seamless を行き来する必要がない。

＋
送信の安全規則に乗る

botress の送信が、seamless の予約、同一内容の重複防止、再送禁止、4段階に乗る。二重送信の防止が一本化される。これは botress 単体では持っていなかった強み。

＋
届いた証拠が強い

Grok Bot の玄関口（gateway）は、受理の記録、会話の項目、echoEntryId（会話に残った印）の3つが揃ったときだけ「届いた」とする。受理だけで済ませない。競合の ack（受け取ったという返事）より厳密。

＋
Grok Bot は「コーディング以外」の入口

Reason はコーディングエージェントの網。seamless は、自分の Grok Bot や ChatGPT Dot へも届く。日常のアシスタントと、開発の会話をつなぐ価値がある。

＋
botress のブランド問題を解消する

「Grok Bot 専用ツール」は単独で OSS にする理由が弱い。seamless の一機能なら、「配線アプリの対応先の1つ」として説明できる。

危ない点

!
法務：botress は「非公開専用」と書いている

botress/README.md は「内部APIの再現と、アカウント固有の情報を含むため公開しない」と明記している。2026-10-16 の判断でも「公開したらまずい」としている。OSS にすると、この判断を覆す。Grok Bot の利用規約、自動アクセス、逆コンパイルの扱いを確認するまで、玄関口は公開しない方が安全。webhook 方式も非公式だが、アプリの保存領域を復号して内部APIを叩く玄関口より、説明と露出は小さい。いずれも法務の専門家の確認が必要。

!
実行環境：Python のパスが固定

src/gateway-send.ts は /usr/local/bin/python3 を固定で使う。Apple Silicon の Homebrew は /opt/homebrew/bin/python3。システムの /usr/bin/python3 は 3.9 で、botress が要求する cryptography が入っていない。初見のMacで動かない可能性が高い。

!
脆さ：非公開の内部APIが3つ

Grok Bot の gateway、Claude の socket（同じMacの中の通信用の口）、Codex の IPC（アプリ同士が話す内部の口）。どれも公式の安定SDKではない。更新で同時に壊れ得る。互換表は Claude 2.1.284/286、Codex 26.930 のままで、現行の 2.1.302 / 26.1007 は未確認。

!
表面積：同じ repo に全部入っている

旧 --registry 方式、status panel、Claude Desktop の band mod、Dot の実験。OSS の README で全部説明すると、何のアプリか分からなくなる。公開する面を削る必要がある。

!
サポート：1人で抱える

Reason は会社とコミュニティがいる。seamless は1人。機能数に比例して issue が増える。v0.1 で約束する範囲を狭くしないと、維持できなくなる。

統合の判定

能力は迎える。repo は抱えない。コア（会話の探索、読み取り、送信、証拠）と、Grok Bot の玄関口アダプタ（Python / Keychain / 内部API）を分ける。玄関口は任意で、入れなくても seamless は動く。webhook 方式は v0.1 から使える。これが、法務、サポート、説明の3つを同時に軽くする唯一の形。

Reason と同じ棚に並ばない。個人のMacで、静かに、確実につなぐ。この一点に絞る。

3つの約束

1
アカウントも常駐もなし。

MCP を1本足すだけ。デーモンも、クラウド中継も、ワークスペースも要らない。

2
いま開いている会話に、そのまま届く。

別プロセスを起こして「成功」としない。会話IDと世代を照合して、その会話へ書く。

3
届いた証拠を残す。不明なら送らない。

受理、到達、処理開始、返答完了を分ける。同じ依頼を二度送らない。結果が分からないときは、分からないと返す。

3つの「しない」

×
チームの網にならない。

招待、名簿、常駐デーモン、P2P。これは Reason の仕事。追わない。

×
クラウド中継をしない。

外部サービスを挟まない。Grok Bot は、自分のアカウントへの直接の道だけ。

×
エージェント実行基盤にならない。

モデルを選ばない。仕事を実行しない。配線だけを持つ。

売り文句の候補

「チームの網は要らない。自分のMacの会話を、ちゃんとつなぐ。」
補足: アカウントなし、常駐なし。Claude Code、Codex、Grok CLI、そして自分の Grok Bot へ。届いたことは、会話で確かめる。

08

判断材料

本質はどこか

統合するかどうか、ではない。公開する範囲をどこで切るかと、誰のための商品にするか。この2つで、サポート量と法務リスクが決まる。

何が変わるか

前: botress は Grok Bot 専用の別ツール。seamless は会話配線。2つのブランド、2つの説明、2つの設定。

後: 1つの配線アプリ。Grok Bot は webhook 方式で v0.1 から使え、玄関口は任意アダプタ。設定は ~/.seamless に寄る。

あなたから見て何が変わるか

作業時間は少し増える（アダプタを分ける分）。その代わり、公開後の問い合わせと法務の説明が減る。Grok Bot のリスクを、本体のリリースから切り離せる。

「全部入り」を諦める代わりに、v0.1 を確実に出せる。出すことが、次の改善を呼ぶ。

最終的な仕様への影響

v0.1 の約束を狭くするほど、後から広げやすい。コアの不変条件（再送しない、受信側の権限を広げない、証拠を残す）は変えない。ここを変えると、seamless の意味がなくなる。

Decision 01

Grok Bot をどこまで v0.1 に含めるか

何を決めるか
既存の webhook 方式までか、botress の玄関口（gateway）まで入れるか。
推奨
webhook まで（A）。玄関口は v0.2 以降、法務確認後の任意アダプタ。
許可すると何が起きるか
Grok Bot の価値を保ちつつ、Python / Keychain / 内部API のリスクを切り離せる。初見の10分で動く。
今回はしないこと
玄関口の公開、botress のレポート、Bot ID、ホスト末尾、アカウント情報の公開。
戻せるか: 戻せる。玄関口は後から足せる。逆に、公開してから引っ込めるのは難しい。
Decision 02

チーム機能を追うか、個人に絞るか

何を決めるか
Reason と同じ「チームの網」を目指すか、1台の配線に絞るか。
推奨
個人の配線に絞る。チームは別製品として考える。
許可すると何が起きるか
機能を増やさず、導入、文脈、証拠に投資できる。試算で 4.0 が見える。Reason と正面衝突しない。
今回はしないこと
P2P、招待、常駐デーモン、クラウド中継、メニューバー。
戻せるか: 戻せるが、チームは別製品として作る方が安い。後から同じ repo に足すと、説明が崩れる。
Decision 03

名前と配布をどうするか

何を決めるか
seamless のまま、npm スコープ + GitHub Releases で出すか。改名するか。
推奨
名前は維持。npm は @chachamaru/seamless。GitHub Releases と npx。
許可すると何が起きるか
既存の repo / URL / 文書を捨てずに済む。検索では埋もれるが、説明とリンクで補える。
今回はしないこと
有料化、Homebrew、PyPI の botress 公開、名前の変更。
戻せるか: 名前は後から変えられるが、リンクと記憶は失われる。今変えるなら早い方が安い。
