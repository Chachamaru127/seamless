# seamless v3 計画案: Reason を超える軸を決めて、そこで勝つ（承認前）

作成: 2026-10-19。v2（consolidated-plan.md）に、調査記録 v3（research-v3-beyond-reason.md）の事実を当てて書き直した。
立場: 製品仕様の正本ではない。承認後に team-plan で spec.md、Plans.md、tasks.md へ分ける。

## 0. 一言

**Reason は自分の網を作る。seamless は、あなたがもう持っている網を束ねる。**
Claude Code の公式メッセージ socket、Codex の `codex queue`、opencode の plugin、Grok Bot の webhook。オンライン機能は製品として持たない（2026-10-19 立花さん判断）。
自前の名簿、鍵、中継、常駐、本文の保存を持たない。届いたかは、相手の記録を読んで言う。

## 1. 「超える」の定義（ここだけで勝つ。総合点では並ばない）

| 軸 | 指標 | seamless v3 の目標 | Reason の現状（出典は調査記録 v3） |
|---|---|---|---|
| 届いたの正確さ | hold、busy、`/goal` 中に「届いた」と誤表示した件数 | 0 件。依頼 ID が相手の記録に現れるまで「預かり」。 | 受信デーモンの ack（stored / delivered / held）。#24 で誤表示があり修正済み。「delivered」≠「読んだ」。 |
| 持たないもの | 追加プロセス数、本文の保存バイト数、ローカル往復で接続する外部ホスト数 | 0、0、0 | デーモン 1、SQLite に本文、既定で n0 中継。 |
| 入口から初回往復 | 導入開始から宛先一覧が出るまでの秒数、1 往復までの操作回数、質問数 | 10 秒、3 操作、0 問 | install + setup + ブラウザ login（または init team）+ エージェント再起動。 |
| 身元と失効 | 自前の鍵・名簿の有無 | OS ユーザーだけ。名簿は Grok Bot の本人登録のみ。 | 自前の署名つき名簿。除名は「暗号的に無力にはならない（for friends）」。 |
| 非コーディングの相手 | 一覧に並ぶ非コーディングの相手 | Grok Bot（webhook）。Dot は phase 2。 | Grok Bot、Muse は Reason MCP 経由（アカウント要否は未確認）。 |

勝てない軸（追わない）: 対応製品数（Reason 10）、チームの名簿と他人のマシン、オフライン郵便箱、LAN/P2P、ask_user の遠隔承認。

## 2. v2 からの訂正（調査記録 v3 の A、B）

1. **Claude の主経路は Channels ではなく、公式の cross-session messaging socket。** 文書が `CLAUDE_CODE_MESSAGING_SOCKET` を「スクリプトやフックから投稿する」用途で公開した。`-p` の会話にも届く。Channels は research preview で、カスタム channel は対話セッション限定、ACK なし。外部イベント（CI、webhook）用の補助に回す。
2. **Codex の書込みは `codex queue --thread`（公式、CLI 0.163.0 で確認）。** ただし保存時点で exit 0 を返し、消費されたかは分からない。Desktop の `/goal` 中は消費されない（#52705）。だから seamless の到達証拠（相手の記録を読む）が差別化になる。Desktop の記録読取りは現行の IPC（内部）か rollout ファイルの受動読取り。公式の読取り口は要望 #54252 が open。
3. **「アカウント不要」「OSS」は seamless だけの売りではない。** Reason のエンジンは `reason-network` CLI を含めて OSS で、アカウントなしの team link モードがある。売りは「持たない」と「届いたの正確さ」に絞る。
4. **「デーモンなし」は看板にしてよい。** v2 は「端末ごとに常駐 hub」としたが、v3 では hub を持たない。状態の所有者は予約ファイル（`~/.seamless/reservations/`）と、各製品の記録そのもの。照会のたびに読む。常駐が要る機能（起こす、見張る）は本人が明示したときだけ `launchd` に置く任意機能にする。

## 3. アーキテクチャ

```
[あなた / 今開いている AI]
   │  seamless "一言"  または MCP 道具（sessions / read / send / status）
   ▼
[seamless CLI（常駐なし。呼ばれたときだけ動く）]
   ├ 探す: Claude は /tmp/cc-socks-<uid> と sessions/<pid>.json、Codex は rollout と IPC owner、Grok CLI は hooks の受信箱、Grok Bot は名簿
   ├ 送る: Claude socket（公式）/ codex queue（公式）/ Grok CLI 受信箱 / Grok Bot webhook（HTTPS）
   ├ 確かめる: 相手の記録を読み、依頼 ID → 到達、ターン開始 → 処理開始、replyTo → 返答
   └ 予約: ~/.seamless/reservations/<id>（hash、状態、時刻だけ。本文なし）
   │
   （遠隔なし。Grok Bot の webhook だけが Mac の外へ出る）
```

- **transport と会話操作を分ける。** ローカルは socket とファイル。Grok Bot は HTTPS webhook。遠隔の transport は持たない。
- **身元は借りる。** OS ユーザーだけ。自前の鍵と名簿を作らない。
- **権限を 4 つに分ける（v2 の採用 7 を維持）。** 閲覧、送信、会話の起動、操作の承認。起動は v1 で持たない（既存会話へ送るだけ。不変条件 2）。承認は持たない（不変条件 3。`humanApproval:true` を書かない）。
- **A2A は phase 3。** 既存 CLI 会話へ注入する口ではない（Codex 応援の指摘）。外部クライアント向けの AgentCard 公開だけを試作する。

## 5. ユーザー体験（v2 の 5 節を維持。変更点だけ）

- 最初の画面は宛先の一覧と送信欄だけ。行ごとに 3 状態（すぐ渡せる / 次の区切りで渡す / 起こすと届く）。
- 状態の言葉は 5 つ（預かり / 渡った / 処理中 / 返事 / 不明）。「渡った」は相手の記録で依頼 ID を見てから。
- **新規: 「相手が hold している」を区別して出す。** Claude の bypass モードや `crossSessionInbound: hold` では、socket への書込みは成功しても相手には届かない。相手の記録に現れなければ「預かり（相手が承認待ち）」と出し、「渡った」と言わない。Reason の #24 と同じ穴を、設計で塞ぐ。
- **新規: Codex の `/goal` 中は「次の区切りで渡す」ではなく「相手が手動 Steer するまで待ち」と出す**（#52705）。

## 8. 確かめること（Yes / No、観測値つき）

1. 初見の Mac で、宛先一覧が 10 秒以内に出る。観測値: 秒数 3 回、質問数 0、変更した設定ファイル数。
2. Claude、Codex、Grok Bot の 3 つが、3 状態のどれかで出る。観測値: 製品数、状態、誤表示 0。
3. `seamless "…"` の 1 コマンドで既定の宛先に届き、返信 ID が依頼 ID と一致する。観測値: ID、秒数、操作回数。
4. 相手が hold（Claude の bypass 組み合わせ、`crossSessionInbound: hold`）のとき、「渡った」と出ない。観測値: 表示された状態、相手の記録に依頼 ID が無いこと。
5. Codex の `/goal` 中に送ったとき、「渡った」と出ず、「手動 Steer 待ち」と出る。観測値: 表示、rollout に依頼 ID が無いこと。
6. 送信直後に切断しても二重送信せず「不明」。照会で相手の記録から判定できる。観測値: 書込み回数 1、最終状態。
7. ローカル 1 往復で、追加プロセス 0、本文の保存 0 バイト、外部ホスト接続 0。観測値: `ps`、`~/.seamless` の中身、`lsof -i`。
8. Grok CLI が manifest + hook 1 枚で追加できる。観測値: コアの差分 0。
9. 公開物に内部 API の再現、アカウント情報、秘密が無い。観測値: スキャン 0 件。
10. Reason との 5 指標の実測値がある。観測値: 表。
11. opencode が plugin だけで追加でき、idle と busy で 1 往復が通る。観測値: コアの差分 0、依頼 ID と返信 ID の一致。

## 9. 停止条件

- S1: 確かめること 3 が週 1 で通らない。→ 製品数を増やさず原因へ戻る。
- S2: 確かめること 4 または 5 が通らない（hold や `/goal` を見分けられない）。→ 「渡った」の定義を「相手の記録で確認」だけに戻し、見分けられない製品は「不明」固定にする。
- S3: 確かめること 7 が通らない（常駐や本文保存が要る）。→ その機能を任意機能へ分け、既定から外す。
- S4: Codex Desktop の IPC が現行版で通らない。→ Codex は CLI（rollout 読取り + queue）だけを正式対応にし、Desktop は未確認と表示。
- S5: 公開物に内部 API やアカウント情報が混ざる。→ 該当アダプタを外す。
- S6: 法務・規約の確認が公開予定日までに終わらない。→ 公開を延期。

## 14. この案の危険

- **Claude の socket は「文書化された挙動」であり、安定 SDK ではない。** `sessions/<pid>.json` と jsonl の形式は内部。版ごとの互換表と `doctor` で軽くする。
- **Codex Desktop の読取りは内部 IPC のまま。** 公式の読取り口（#54252）が出るまで、Desktop は「未確認」表示を許容する設計にする。
- **Reason も同じ公式経路を使う。** 速さで勝つ根拠はない。勝つのは正確さと持たないこと。
- **チームを求める利用者には届かない。** それは Reason の仕事と書き、併用（同じ会話に二重配線しない）を README に書く。

## 15. 2026-10-19 の本人判断（反映済み）

3. Codex Desktop の内部 IPC は読取りに使い続ける。
4. Reason の比較導入は同じ OS ユーザーで行う。条件: setup が書き換える設定ファイルの backup を先に確認、同じ会話に両方をつながない、計測は順番、終わったら leave → setup --remove。
