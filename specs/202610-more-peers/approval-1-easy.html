seamless の相手を増やす計画 ── 承認 1 回目の判断材料

今日の判断は 1 つだけです。「計画の土台（spec）をこの内容で進めてよいか」。実装はまだ始まりません。

ひとことで

いま seamless は「同じ Mac の Claude と Codex の会話」だけをつなぎます。この計画は、相手を Grok CLI（ターミナルで動く Grok）、Grok Bot（クラウドで動く Bot）、ChatGPT Dot にも広げます。

実際にはどういうこと

今できていること: Claude の会話から Codex の会話へ「この件、確認して」と送ると、相手に届き、相手が読み、返事が戻る。その 4 段（受け付けた、届いた、読んだ、返事が来た）を seamless が見張っています。

この計画の後: 同じことを Grok CLI と Grok Bot（後で Dot）にもできるようにします。ただし相手ごとに事情が違うので、できる範囲が違います。

相手正体できることできないこと（今の時点）
Grok CLIこの Mac のターミナルで動く Grok一覧に出す、読む、送る、返事を受ける相手が何もしていない間は届かない。相手が 1 手終えた瞬間にしか文を足せない（Grok 自身にそういう口しか無い）
Grok Botクラウドで動く Bot。この Mac にはいない送る（受け付けた、だけ分かる）、Bot からの返事を受ける一覧と本文を読むことは無理。「届いた」「読んだ」は Bot 側の仕組みでは分からない
ChatGPT Dot調査中未定（資料待ち）未定

いちばん大事な変更（本質）

seamless には「製品の約束」が 8 つあります。そのうち 8 番「相手は同じ Mac の Claude と Codex だけ。登録なしで自動で見つける」を書き換えます。

前後
相手は同じ Mac の Claude と Codex。自動で見つけるMac 内の会話（Claude、Codex、Grok CLI）は今までどおり自動で見つける。
外の相手（Grok Bot、Dot）は、立花さんが名簿に登録し、鍵で本人確認したときだけ相手にする

「鍵」は、Bot が本物だと確かめるための秘密の文字列です。立花さんが Mac の環境変数（=アプリに渡す設定の値）に置き、seamless は読むだけ。記録にも会話にも書きません。

変わらないこと（守りの線）

1名乗りだけで相手を信用しない（「私は Bot です」と言っても鍵が無ければ拒否）
2届いた文は、立花さんの承認の代わりにならない（届いた文で送信、削除、課金、マージはしない）
3送れたか分からないとき、勝手に送り直さない
4同じ会話を別のプロセスで開き直して「届いた」ことにしない
5外からの入口（公開 URL、待受サーバー）が要る設計になったら止まって聞く

具体例（Grok CLI に送るとき）

Claude の会話から Grok CLI の会話「seamless · main」へ「lsof の回数を数えて」と送ります。

受け付けた 11:40 → 届いた（Grok が次の 1 手を終えたとき）→ 読んだ → 返事

Grok が待機中（立花さんが何も打っていない）なら「届いた」で止まります。そのとき帯に「Grok は待機中。届くのは次の 1 手の後」と出す案を勧めています。

なぜこの形か

Grok 自身に聞いた結果、動いている会話へ外から文を入れる正式な口が無いと分かりました（確信度 高）。唯一の道が「1 手の終わりに文脈へ足す」仕組みです。別のプロセスで同じ会話を開けば入れられますが、それは「同じ会話に届いた」ことになりません（約束 2 番に反する）。

Grok Bot は、外からの入口が webhook（=決まった住所に文を送ると Bot が起きる仕組み）しか無く、「受け付けた」までしか分かりません。だから「届いた」「読んだ」は未確認のまま表示します。分からないことを分かったふりにしない、が seamless の約束 4 番です。

承認するとどうなるか

1私が製品の約束 8 番を書き換え、承認の記録を残します。
2次に「どう作るか」（Plans.md）と「1 回の作業の単位」（tasks.md）を書きます。
3図面検査（別の AI が食い違いを探す）と敵対（別の AI が穴を探す）を通します。
4その後に承認 2 回目をお願いし、そこで初めて実装に入ります。

後戻り: 8 番を元に戻すだけで戻せます。実装前なので、コードは何も変わっていません。
