純正とseamlessの会話探し

Claude 純正の会話探し（ListAgents と SendMessage）は、Claude の会話へ短い伝言を渡すための仕組みです。seamless は、Claude と Codex の会話を作業フォルダで絞って見つけ、中身を読み、頼み、返事まで追うための仕組みです。

Claude 宛ての配達は、どちらも同じ受け口（会話ごとに開く Unix ソケット）を通ります。違いは「誰を見つけられるか」と「届けた後に何が分かるか」にあります。

それぞれ、どうやって相手を見つけているか

Claude 純正
  1. Claude Code は会話を始めると、その会話専用の受け口（Unix ソケット）を開く。
  2. ListAgents は、受け口を開いている会話を並べる。Remote Control に接続中なら、クラウドと別の機械の会話も Anthropic のサーバー経由で加わる。
  3. 宛先は名前で指す（例: 「シームレス [29ace3]」）。同じ名前が複数あると、角括弧の短い識別子で区別する。
  4. SendMessage が伝言（文字だけ）を相手の受け口へ送る。
seamless
  1. 道具を呼んだ会話を実測で特定する。Claude は親プロセスと署名、Codex は道具の呼出しに付く会話ID（_meta）で決める。
  2. Claude は稼働記録 ~/.claude/sessions/<pid>.json を読み、プロセスが生きているか、受け口の持ち主、実際の作業フォルダを照合する。Codex は Codex Desktop の会話記録を読み、Desktop に持ち主を問い合わせる。
  3. 作業フォルダで絞る。止まっている会話は隠して件数だけ返す。一覧を作るときに本文は読まない。
  4. 送るときは、Claude へは純正と同じ受け口、Codex へは Codex Desktop の内部の接続を使う。
二つの道が重なる所 seamless が Claude へ送る依頼は、純正の受け口に入ります。そのため、届いた後の扱い（待機中なら新しいターン、作業中なら道具の呼出しの合間に読む）と、受け手側の受け入れ設定 crossSessionInbound は、純正の伝言と同じに効きます。

同じ一言を頼んだら、どう動くか

「同じ作業場所の Codex に、さっきの変更を確認してもらって」

純正だけの場合
  • ListAgents の109件に Codex は1件も無い。
  • 宛先が見つからず、ここで止まる。

届かない

seamless の場合
  • sessions で同じ作業フォルダの4件から Codex を選ぶ（2件あれば選択肢を示して止まる）。
  • read で、その Codex が直前に何をしていたかを読む。
  • send に track を付けて送り、返答完了まで段階を追う。

届いて、返事まで確かめられる

相手が Claude なら、純正でも届きます。その場合の差は、109件から名前で選ぶか、作業フォルダで4件に絞ってから選ぶか、そして届けた後に相手の作業を読めるかどうかです。純正の一覧の結果には作業フォルダが入らないので、純正だけでは名前が唯一の手がかりになります。

Desktop アプリには三つ目の道もある

Claude Desktop の中の Claude は、アプリの道具 list_sessions と search_session_transcripts も使えます。list_sessions は Desktop の会話をタイトル、作業フォルダ、ブランチ、PR 付きで並べます（今回も先頭5件にフォルダとブランチが出ました）。search_session_transcripts は他の会話の記録を全文検索し、一致した所の抜粋を返します。対象は Desktop の Claude 会話だけで、Codex は入りません。送信はアプリの説明上 SendMessage を勧めています。

なぜ二つに分かれているのか

純正の仕組みは、ある会話で分かった発見や決定を、別の会話へ伝えるために作られています。権限は会話ごとに閉じていて、伝言で相手の権限を借りることはできません。履歴ごと引き継ぎたいときは会話の再開を使う、というのが公式の説明です。

seamless は、Codex を相手に含めることと、元の会話をそのまま読むことを目的に作りました。Codex の会話は Claude の受け口を開かないので、純正の一覧には仕組みの上で出てきません。そこで seamless は、Claude 側は純正の受け口に乗り、Codex 側は Codex Desktop の接続に乗る形を取っています。

判断材料

本質

Claude 同士の配達は、純正と seamless で同じ受け口を使う。seamless が足しているのは、Codex を含めること、相手の中身を読むこと、作業フォルダで絞ること、返事まで追うことの四つ。

何が変わるか

前: 純正だけなら、Claude にだけ伝言を送れる。
後: seamless を足すと、Codex にも送れ、相手の作業を読み、返事の到着を確かめられる。

立花さんから見て

「Claude に伝えて」はどちらで頼んでも同じ受け口に届く。「Codex に」「何してたか見て」「返事来た？」は seamless でしかできない。

仕様への影響

今すぐ変える所は無い。候補として、Claude 同士の送信を純正に任せて seamless を読む追うに絞る案はある。推奨は現状維持（seamless で送ると追跡と送り主の照合が付くため）。後から戻せる。

追加で確かめた2点

純正の一覧に作業フォルダは出るか

出ない。Remote Control に接続していない試験用の会話（Claude Code 2.1.289、claude -p）で ListAgents を呼び、生の結果を取り出しました。15件のどの行にも作業フォルダはありませんでした。Remote Control の有無とは関係なく、道具の結果に作業フォルダが入らない作りです。同じ名前の会話が複数あるときに出るかは試していません。

seamless の依頼は保留されるか

受け手が権限確認を飛ばす設定のときだけ保留される。seamless が送る1行には、送り主の権限モードを名乗る欄がありません。道具も MCP も持たない試験用の Claude を2つ立てて、同じ形の1行を送りました。

  • 通常の権限モード（default）の受け手: 届いて、返事 PONG-A1 が出た。
  • 権限確認を飛ばす受け手（bypassPermissions）: 届かずに保留。記録は peer_message_hold、理由は no-mode-asserted（送り主が権限モードを名乗っていない）。

Desktop の会話がふだん使う auto、acceptEdits、default では保留されません。権限確認を飛ばす会話に届けたいときは、受け手側で crossSessionInbound を accept にします。送り主が「権限確認を飛ばしている」と偽って名乗れば届きますが、seamless は名乗りを偽らない方針です。

確かめきれていないこと

  • seamless の範囲 any は、Codex の会話を新しい順に50件だけ確かめます。今回は残りの 8,730件を確かめていません。
  • この会話は Desktop 同梱の Claude Code 2.1.286（対応表で確認済み）で動いています。対応表に無い CLI 2.1.289 の会話からも、更新後の seamless は止まらずに一覧を返しました（呼ぶ側は「未確認」と表示）。
  • 純正の挙動は、公式文書と今回の実行結果に基づきます。純正の受け口の内部の形は、公開された取決めではありません。
