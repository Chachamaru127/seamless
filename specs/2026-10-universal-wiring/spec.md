## 何を

同じ Mac で開いている AI の会話と、本人が名簿に登録した外の実行主体に、今の会話から一言を届け、届いたかを相手の記録で確かめ、返事を同じ場所に出す。公開 OSS（MIT 予定。H5）として第三者が導入できる形にする。

対象の相手（v1）: Claude Code、Codex（CLI と Desktop）、opencode、Cursor CLI、Antigravity CLI、Grok CLI、Grok Bot。
対象外（phase 2 以降）: ChatGPT Dot、Claude Code Channels を使う外部イベント、A2A。

本人の指示の出典: 2026-10-19 「オンライン機能は不要」「opencode を入れて」「Cursor CLI、Antigravity CLI は入ってるから入れて」「それ以外は OK」（それ以外 = 計画案 v3 の v1 範囲: Claude Code、Codex、Grok Bot（webhook まで）、Grok CLI）、「やるべきことを Issue に積み、30 分に 1 回 Issue を解決するループを回して閉ループ運用に」「実装作業系は DeepSeek 1017 で」、「1. 承認」（spec.md と Plans.md）。

## なぜ

- 競合 Reason Network は「チームの網」を作る。seamless は、利用者がもう持っている各製品の公式経路を束ねる。勝つ軸は 4 つ。届いたの正確さ、持たないもの（常駐なし、本文の保存なし、ローカル往復で Mac の外へ出ない）、入口から初回往復までの速さ、チーム用の鍵と名簿を作らないこと。
- 類似製品（agmsg）は「人間が手で起動する」ために定着しなかった。走っている会話の中から 1 行で呼べることを守る。
- Codex の queue と Claude の socket は「書き込めた」までしか教えない。相手の記録を読んで「渡った」「処理中」「返事」を区別することが、seamless の価値。

## 用語

- 相手: 一覧に出る会話または実行主体。不変条件 1 のとおり製品、ホスト（v1 は同じ Mac のみ）、会話、実行主体で特定する。会話は ID と世代で区別し、作業場所は候補を選ぶ条件に使う。
- 段階（不変条件 4 の記録単位。順に進む）:
  1. 受理: 窓口が依頼を予約し、相手への書込みが成功した。
  2. 渡った: 相手自身の記録に依頼 ID が現れた。
  3. 処理中: その依頼を含むターンが始まった記録がある。
  4. 返事: replyTo が依頼 ID と一致する返事を相手の記録で読んだ。
  5. 不明: 書込み後に成否が分からない状態（不変条件 6）。段階 1〜4 の記録とは別に持ち、再送しない。
  内部名との対応は Plans.md 1 章に置く。
- 保留中（状態。段階ではない）: 受理の後、相手の記録を読めたのに、一定時間（Plans.md の Open decision 1）を過ぎても依頼 ID が現れない。理由を添える。Claude の受信設定が hold、または権限モードの組み合わせで hold になっている。Codex Desktop が目標実行中で外からの依頼を取り込まない。理由が分からない。
- 保留中と区別する状態: 記録が読めない（読取り失敗。段階は受理のまま、理由を添える）。相手が拒否した（公式経路が拒否を返した。段階は受理に進まず、理由を添える）。遅延（一定時間の前）は「受理」のまま。
- 公式経路: その製品の公開文書にある口。Claude のセッション間メッセージの受信口、Codex の queue、opencode の plugin、Cursor と Antigravity と Grok CLI の hooks、Grok Bot の webhook。
- 内部依存: 公開文書にない形式やファイル。互換表で版ごとに確認し、表にない版は「未確認」と表示して止めない（既定）。
- 人の確認の印: 届いた文は本人の承認の代わりにならない（不変条件 3）。承認を意味する印は書かず、人の確認を促す印は制限の設定で本人が有効にしたときだけ付ける（不変条件 3 の 2026-10-04 決定を維持）。

## 持たないもの（製品の思想。2026-10-19 立花さん判断）

- 常駐プロセス。起こす機能が要るときだけ本人が任意で OS の定期起動に置く。
- オンライン機能。別マシン、P2P、中継、郵便箱、SSH 遠隔。Grok Bot の webhook（HTTPS）だけが Mac の外へ出る。
- チーム用の鍵、署名つき名簿、招待。同じ Mac の相手は OS ユーザーで特定する。外の実行主体（Grok Bot）は不変条件 8 のとおり本人の名簿と鍵で確かめる。
- 会話本文の保存。予約は hash、状態、時刻だけ。次ターンで届く製品（Cursor、Antigravity、Grok CLI）の受信箱に本文が滞留するのは配達までで、配達後は残さない。
- 独立した受信箱アプリ。返事は送り先の画面に出る。

## 受け入れ条件（AC。Yes / No で判定。観測値つき。検証の手段は Plans.md 8 章）

### 入口
- AC1: 初見相当の環境（一時のホーム、seamless の MCP 登録なし、Keychain を読まない、対象製品は動いている）で、導入開始から宛先一覧が出るまで 10 秒以内。観測値: 3 回の秒数、本人への質問数 0、導入が変える設定ファイルの数（MCP の登録 1 件だけ）。
- AC2: 一覧に、動いている対象の相手が 3 状態のどれかで出る。3 状態の判定: すぐ渡せる = 公式経路で今すぐ書込みができ、相手が待機中。次の区切りで渡す = 書込みはできるが相手が作業中、または hooks で次ターンに届く製品（待機中なら人が次のターンを始めるまで届かない）。起こすと届く = 相手が休止中で、起こす操作が要る。製品ごとの判定表と内部名は Plans.md 3 章。観測値: 製品数、各行の状態、誤表示 0（相手の実際の状態と突き合わせ）。
- AC3: 1 コマンドで既定の宛先に届き、返事の replyTo が依頼 ID と一致する。観測値: 依頼 ID、返信 ID、秒数、本人の操作回数 3 以下。実相手で確かめる（人の作業）。

### 届いたの正確さ
- AC4: 相手（Claude）が hold のとき、「渡った」と出ず「保留中（受信設定）」と出る。観測値: 表示、相手の記録に依頼 ID が無いこと、相手の受信設定の値。
- AC5: 相手（Codex Desktop）が目標実行中のとき、「渡った」と出ず「保留中（手動の取り込み待ち）」と出る。観測値: 表示、相手の記録に依頼 ID が無いこと。
- AC6: 送信直後に切断しても二重送信せず「不明」。同じ依頼 ID の再呼出しは新しい配送にならない。照会で相手の記録から段階を判定できる。観測値: 相手の記録への書込み回数 1、最終段階。
- AC7: 「渡った」は相手の記録に依頼 ID が出現したときだけ。実相手で 15 往復（Claude 5、Codex 5、Grok Bot 5。待機中、作業中、hold / 目標実行中、休止中を含む）を行い、書込み成功だけで「渡った」と出した件数 0。観測値: 15 件の記録（本文なし）。

### 持たないもの
- AC8: ローカル 1 往復で、往復後に残る seamless のプロセス 0、往復完了後に seamless の保存先と受信箱に残る本文 0 バイト、往復の間（1 秒ごとの標本）に seamless 自身のプロセス（起動した hook と plugin を含む）から Mac の外への接続 0。相手の AI 自身のモデル通信は対象外。観測値: seamless のプロセス一覧、保存先と受信箱の中身、seamless のプロセスに限った接続の標本。

### 対応製品
- AC9: 新製品の追加が、製品ごとの定義ファイル 1 枚、製品側の hook または plugin 1 枚、製品ごとのアダプタ 1 ファイルで済み、共通部分の差分が 0。観測値: 追加の commit で共通部分の差分行数 0。
- AC10: opencode が plugin だけで追加でき、待機中と作業中の両方で 1 往復が通る。観測値: 依頼 ID と返信 ID の一致（実 opencode。人の作業）。
- AC11: 対応表に v1 の 7 製品すべての行があり、各行に製品、版、接続方式、状態、確認日がある。表にない版は「未確認」と表示して止めない。Codex Desktop の接続が現行版で通らないときは「未確認（Desktop）」と表示する。観測値: 対応表の行数 7 以上、一覧の版の状態。

### 公開
- AC12: 公開物に、アカウント固有の情報（Bot ID、ホスト名、アカウント照合値）と秘密が無い。内部依存は 2 種に分け、一覧にして公開物の説明に載せる。各製品の内部形式の受動的な読取りは許す。内部 API の再現（公開文書にない通信手順をコードで再現したもの。v1 では Codex Desktop の内部接続の読取りだけで、使用は H2 で決定済み）は、一覧に載せたものだけ許す。公式経路（webhook、hooks）の規約確認は H6。観測値: 秘密スキャン 0 件、同梱物の一覧、内部依存の一覧（H2 の記録つき）。
- AC13: Reason との 5 指標の実測値がある。最初の画面までの時間、初回往復時間、操作回数、既存会話への復帰成功率、届いた表示の正確さ。観測値: 表（人の作業。H3）。

### T3 Code との相性
- AC14: T3 Code の会話から seamless の道具を呼び、同じ Mac の Claude Code、Codex、opencode へ送って、返事の replyTo が依頼 ID と一致する。2026-10-19 時点で未実測。観測値: 3 製品の依頼 ID と返信 ID（人の作業）。
- AC15: 照会の出力だけから、T3 Code の返信内の表示で 5 段階の進み具合を出せる。表示の段階が照会の出力と一致し、本文を含まない。2026-10-19 時点で未実測。観測値: 表示と出力の突き合わせ。
- AC16: 受信口を持たない Claude のプロセス（観測した範囲では T3 Code が起動したもの）が、一覧に「受信不可（受信口なし）」と理由つきで出る。観測値: 一覧の表示。

## 停止条件（AC に対応）

- S1: AC3、AC7 が週 1（T15 の計測を実行する人 = 立花さんまたはリーダー）で通らない。→ 製品数を増やさず原因へ戻る。
- S2: AC4、AC5、AC6、AC7 のいずれかが通らない。→ 見分けられない製品では「渡った」と「処理中」を出さず「受理」止まりにし、返事（replyTo の一致）だけを証拠にする。
- S3: AC8 が通らない。→ 常駐や本文の保存を要する機能（起こす機能、受信箱の滞留、照会の cache）を任意機能に分け、既定から外す。
- S4: AC11 の Codex Desktop が現行版で通らない。→ Codex は CLI だけを正式対応にし、Desktop は「未確認（Desktop）」表示。
- S5（H1 に対応）: Antigravity CLI（T3 Code が管理する版）に、外から会話を見つけて注入する hooks または公式の口が無い。→ Antigravity を phase 2 へ送り、H1 の範囲変更として記録する。
- S6: AC12 が通らない。→ 一覧に載っていない内部 API の再現を含むアダプタ（候補: Codex Desktop の内部接続、Grok Bot の玄関口）を公開物から外す。
- S7（H5、H6 に対応）: H6 の規約確認が H5 で決めた公開日までに終わらない。→ 公開を延期。
- S8（H7 に対応）: 30 分ループで、連続 3 回が blocked になる、作業ツリーが汚れて着手できない、または着手中が 90 分を超える。→ ループは休止の印を置いて自分では取らなくなり、人が印を外すまで再開しない。
- S9（AC8 に対応）: seamless のプロセスから Mac の外への接続が観測された。→ その経路を既定から外し、原因が分かるまで該当製品を「未確認」表示にする。
