## 指摘

**F1（中。P2 の前に修正必須）** `src/git-context.ts:42-45`

- **仕組み**: git の `-c` は最初の `=` で key と value を分けます。repo の config に `[filter "x=y"] clean = <cmd>` と書き、`.gitattributes` で `filter=x=y` を指定したとします。このとき無効化のつもりの `-c filter.x=y.clean=` は、`filter.x` に値 `y.clean=` を入れる指定として解釈されます。本物の `filter.x=y.clean` は残るので、status が中身を比べる場面で `<cmd>` が実行されます。
- **確度**: git 本体の実装知識による静的な判断です。指定外のコマンドは禁止なので、実行での再現はしていません。
- **P1 の到達経路**: 手動の `cli context <path>`（`src/cli.ts:10`）だけです。
- **最小修正**: ループ内に `if(key.includes('='))return unknown('invalid_output');` を足して fail-closed にします。fixture に `filter "x=y"` が実行されないことの試験を1件追加します。
- **evidence.md の記述**: T2 の「filter/fsmonitor未実行 PASS」は、通常の driver 名に限った結果です。

**F2（低）** `select` は、候補0件と、全員が新しい観測で offline の場合を、どちらも `no_candidates` で返します（`src/discovery.ts:86-92`）。明示 target が offline のときも同じです。spec.md:24 は「候補0件、停止、metadata 不明」の区別を求めていますが、区別できるのは sessions の reason だけです。誤った相手へ送る方向の問題ではなく、fail-closed です。

**F3（低）** 新しい観測で offline でも、Git context が unknown だと rank が null になり、全体が blocked_unobserved になります（`src/discovery.ts:58`, `88`）。spec.md:67 は「信頼した停止観測だけ除外可能」としているので、それより保守的です。

**F4（低）** `open` に O_NONBLOCK がありません（`src/registry.ts:21`）。名簿のパスを FIFO（名前付きパイプ）に差し替えると、その要求が返らず serve が止まります。同じ OS ユーザーは名簿を書き換えられる前提なので、可用性だけの問題です。
