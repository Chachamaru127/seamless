## 全体の形

seamless は「製品ごとの観測と配送の部品（アダプター）」を、共通の一覧・読む・送る・段の観測の上に載せている。今回は部品を 2 種類足す。

1. Mac 内の製品の部品（Grok CLI）: Claude と Codex と同じ型。会話の記録を読み、動いている会話のプロセスを実観測で特定し、その会話の実行主体へ届ける。
2. 外の実行主体の部品（Grok Bot、後に Dot）: プロセスが手元に無い。名簿の登録（宛先の住所、送り手の鍵の置き場所、許す操作と範囲）を正本にし、送りは住所へ、受けは鍵で確かめる。

共通の変更は 3 つだけに絞る。製品の種類に `grok` と外の実行主体を足す。呼び手の特定に「Grok CLI の祖先」と「名簿と鍵で確かめた外の送り手」の 2 つの道を足す。段の観測に「未確認のまま残す段」を増やす。

封筒の印はルートの spec.md の不変条件 3 の定義に従う（ここに写さない）。今回足す 3 経路（Grok の受信箱へ置く封筒、webhook へ送る封筒、Bot から受ける封筒）は、limits.json を読む新方式に乗せ、既存の経路と同じ規則にする。

## P1 Grok CLI の作り

観測（一覧と読む）
- 動いている会話: Grok の稼働中の会話の台帳 `~/.grok/active_sessions.json`（会話 ID、pid、作業場所、開始時刻。以下「台帳」。外の実行主体の「名簿」peers.json とは別）を読み、pid が生きていて開始時刻が合う行だけを「動いている」とする。世代 = `pid@台帳の opened_at`（台帳の文字列そのもの）。生きているかは ps の開始時刻で確かめ、開始が opened_at の 1 秒後まで（ps は秒単位）なら同じプロセスとする。使い回された pid は行より後に起動したプロセスなので、この上限で弾く。下限は置かない（実測で起動から台帳の登録まで 9 秒かかった例があり、`/new` や `/resume` で会話を後から開くこともある。2026-10-08 の点検で 120 秒の下限を外した）。画面なし（`grok -p`）は登録されないので対象外。台帳の行でも、要約が無いか `session_kind` を持つ会話（画面なし、下請け）は出さない。同じ会話の生きている行が 2 つあるときは、どちらも送信前から存在した「その会話」と言えないので、状態を unknown にして宛先にしない（チケットを出さない）。版が許可外（版の表で fix_required、または strictVersions のときに verified でない。1.0.46 は checking なので strictVersions では allowChecking が要る）のときは、動いていても unknown（理由 unsupported_version）にして宛先にしない。unknown の会話は、止まっている会話と同じく既定の一覧では隠れて offlineHidden に数えられ、includeOffline のときに出る（Claude と Codex と同じ）。
- 止まっている会話: 会話の保存先にあって要約に `session_kind` が無い会話（画面ありの会話。T0-1 の実測で、画面ありの要約には `session_kind` が無く、画面なしは `headless`、下請けは `subagent` か `subagent_resume` が入る）のうち、台帳に無いもの、または台帳にはあるが pid が生きていないか開始時刻が合わない行（台帳の刈り残し）。画面なし（`grok -p`、`session_kind` が headless）と下請け（`subagent`、`subagent_resume`）の会話は、動いていても止まっていても一覧に出さない（対象外）。Codex と同じく既定では一覧に出さず offlineHidden に数え、includeOffline のときだけ「止まっている」として出す（AC1 の区別）。範囲が「すべて」のときは、止まっている会話を最後に動いた時刻の新しい順に 50 件までにする（Codex の一覧と同じ上限。台帳に残った行は数えない）。台帳に行が無い止まっている会話は世代を持たない（`none`）ので、前回見た会話の記録（seen.json）には入れない（再び起動した直後に「世代が変わった」と誤って unknown にしないため）。その作業場所は、保存先のフォルダ名（作業場所の URL エンコード）を戻して実体の道にしたものを使う。宛先にはしない（D3）。一覧の各行は製品 `grok`、ホスト local、会話 ID、世代、状態を持つ。
- 本文: `~/.grok/sessions/<作業場所>/<会話 ID>/updates.jsonl` を読み、`user_message_chunk` と `agent_message_chunk` を連結して可視の発話にする。`tool_call` は道具の呼び出し。思考（`agent_thought_chunk`）と生の履歴（chat_history.jsonl）は読まない。
- 範囲: 作業場所は台帳の `cwd` を使い、Claude と Codex と同じ範囲判定（specs/202610-everyday-use/spec.md の探す範囲。既定は不変条件 8 のとおり同じ作業場所で、同じリポジトリとすべては本人が制限の設定で選んだときだけ。Grok のために広げない）に乗せる。範囲外の Grok の会話は一覧、読む、送るのどれも拒否する（AC8）。Grok には「範囲の未設定」が無い（範囲は台帳の作業場所から決まる）ので、AC8 の「未設定」は「台帳の行の作業場所が無いか読めない」に当たり、その会話も拒否する。制限の設定（limits.json）が壊れているときは既存と同じく拒否する。

配送（送る）。封筒は会話ではなく「会話の世代」に宛てる
- 受理: seamless が受信箱 `~/.seamless/grok-inbox/<会話 ID>/pending/<送り手と依頼 ID の組の SHA-256>.json` に封筒を書き終えた時点（別の会話が同じ依頼 ID を選んでもぶつからないよう、予約と同じく送り手を名前に含める。2026-10-08 の穴探しで直した）（spec の段の定義の Grok CLI の但し書き）。封筒には宛先の世代（pid と開始時刻）を書く。同じ依頼 ID が pending、handed、delivered、failed、unknown のどこかにあれば置き直さない。別 ID で同じ内容（送り手、宛先、replyTo、本文が同じ）も、既存の予約（依頼の hash の claim）に乗せて、前の依頼が成否不明か処理中の間は `duplicate_of_unknown` にする（AC7。Bot の経路と同じ仕組み。前の依頼が受理か不受理で終わった後の同じ内容は、本人か AI が改めて頼んだ新しい依頼として受ける。Claude と Codex と同じ）。同じ依頼 ID は予約の記録から前の結果を返し、置き直さない。予約の記録が無いのに受信箱に同じ依頼 ID がある（予約の外で置かれた）ときは、置き直さずに成否不明（unknown）とする。本文が 8,000 字を超える封筒は、送る時点で `text_too_long` として拒否する（切り詰めて欠けさせない。上限の由来は D7）。
- hook のスクリプト: seamless のリポジトリにある固定の道（`src/grok-hook.ts`）を、Node の絶対パスで起動する。会話 ID と作業場所は Grok が hook に渡す入力（標準入力の JSON。項目は T0-2 で確かめる）から取り、Grok の TUI の pid（hook のプロセスの親 `process.ppid`。T0-2 で台帳の pid と一致を確認、間にシェルは挟まらない）と台帳の行を照合する。hook の入力は camelCase（sessionId、cwd、reason、stopHookActive、promptId）。1 手の終わりの reason は `end_turn`、会話の終わりは `shutdown`。封筒の世代と一致しないときは配達しない（別プロセスが同じ会話を開いても届かない。AC2）。
- 1 回の Stop で 1 封筒。文を足すと Grok は同じ手の続きを 1 回走らせ、続きの回の Stop（`stopHookActive: true`）でも hook が呼ばれるので、次の封筒はその回で届く（Grok の続きの上限は 1 手に 8 回）。順は受理の時刻。`pending` → `handed`（hook の pid を名前に入れた原子的な改名。改名できなければ別の hook が取っている）→ 文脈に足す → 受領記録を書く → `delivered`。壊れた封筒と、この会話あてでない封筒は `failed` に移して次へ進む（先頭で止まらない）。`handed` のまま残った封筒（取った hook が、記録を書く前に死んだ）は、文脈に入ったかが分からないので戻さず、取った hook の pid が生きていなければ次の hook が `unknown` に移す。帯は「成否不明。立花さんの確認が要る」と出す（成否不明の自動再送をしない。AC7）。2026-10-08 の点検で、取ってから返すまでの間だけを表す `delivering` と、それを `pending` に戻す回収を外した（その間は改名 1 回分で、そこで死んだ封筒も成否不明として扱えば約束は守れる）。
- 会話の終了時の Stop（`channel_closed`、`shutdown`）では配達しない。封筒は pending のまま（まだ配達していないので再送ではない）。
- 配信確認: hook が `delivered/<依頼 ID>.json` に受領記録（依頼 ID、会話 ID、世代、hook の時刻、Stop の理由）を書き、かつ Grok の記録に、受領記録の hook の時刻以降で、同じ会話の次の `user_message_chunk` より前にある `hook_execution`（`event_name` が `stop`、`runs[]` に seamless の hook の名前があり、その `status.status` が `success`）がその受領記録の後の最初の Stop の行で、さらにその直後に Grok が渡された文を記録した `hook_annotation`（「↩ Stop hook feedback, continuing: 」に続く全文。T0-2 の実測）に、この依頼 ID と送り手を書いた seamless の封筒の行がある時点。hook_execution の行には依頼 ID が入らないので、依頼 ID は hook_annotation で結ぶ。本文に偽の封筒の行を書かれても、seamless の封筒の行は文の最後に置くので、最後の印の後の行だけを読む。文を足すと Grok が同じ手の続きを走らせ、続きの回の Stop の行がもう 1 件できるので、受領記録の後の最初の Stop だけを数える。別の手の Stop は必ず次の利用者の発話の後に来る。受領記録だけ、記録だけ、受領記録の後に次の利用者の発話を挟んで別の Stop の hook_execution だけ、のどれでも立てない（AC2 の「無関係な発話や返信をその依頼の段にしない」）。会話の終了時の Stop（`channel_closed`、`shutdown`）は Grok が無視するので、hook はその理由では何も取らない（封筒は pending のまま）。
- 処理開始: 受領記録の時刻より後に、同じ会話の記録に相手の発話か道具の呼び出しが現れた時点（Claude と Codex と同じ近似。依頼の内容への反応かどうかは判定しない）。
- 返答完了: 相手が seamless の `send` で `replyTo` つきに返した時点。
- 一覧の状態の値と帯の言葉: 動いている会話は `online`（帯の表示は「動いている」）、止まっている会話は `offline`（帯の表示は「止まっている」）。既存の Claude と Codex と同じ値と言葉。
- 見せる場所: 帯（Claude Desktop の入力欄の上の 1 行）と、パネル「チーム」（帯の ×n で開く一覧。帯の第 4 版の設計 specs/202610-status-ui/design-v4.md）。
- 宛先の世代の生きた行が台帳に無いとき、pending の封筒は、その世代の hook しか渡さないので、このままでは渡らない。帯は「宛先の会話は台帳から消えている。このままでは届かない」と出す（台帳から推した表示で、届かなかったことの観測ではない）。台帳が読めない（壊れた JSON、所有者違い）ときは判断せず pending のまま。台帳のファイルが無いのは Grok の画面が 1 つも動いていない状態（終了後は `[]` が残ることを T0-1 で観測）なので、空として扱う。
- 未配信の表し方: 配信確認が無い間は「受理・未配信」と出し、「待機中」とは断定しない。相手の記録に 5 分以上の動きが無いときだけ「相手は 5 分以上動いていない。次の 1 手の後に届く」と添える（D5 の (b)）。hook が登録されていない、失敗した、途中で止まった、の区別は受領記録と `hook_execution` の有無から出せる範囲でだけ出す。
- 封筒の印は「全体の形」の節の規則のとおり（ルートの不変条件 3 に従う）。
- 本文が 8,000 字を超える Grok 宛ての送信は、検証の後、予約を作る前に `text_too_long` で止める。旧方式の名簿（registry）は Claude と Codex の登録しか受けないので、Grok 宛てはこの経路に乗らない。
- H0 の判断（済み、2026-10-08）: `/hooks-trust` は試験用の場所ではなく git のリポジトリの根元（seamless 全体）を信頼した（Grok はリポジトリの根元の `.grok/hooks/` だけを読む）。T0-2 の試験用 hook は根元に一時的に置き、試験用の場所の会話のときだけ動くように絞って使い、試験の後に消した。信頼は立花さんの判断 C で外す（`/hooks-untrust`）。実配送の hook は H1（信頼の操作が要らない全体の置き場所）で入れる。

呼び手（Grok CLI → Claude、Codex）
- 祖先に Grok の実行ファイル（`~/.grok/bin/grok`。署名の確認は T0-3a。確かめられなければ、T0-3b の代わりの確かめ方（実体の道とハッシュの固定）に本人の「可」（H8）が出るまで T1-7 に入らない。H8 が「否」なら AC3 は未達として閉じる）があり、その pid が 台帳の行と一致し（行の生存の確かめ方は一覧と同じ）、行の作業場所がプロセスの作業場所と一致し、実行ファイルが X.AI の署名（TeamIdentifier 5Y6N3AJ54S、T0-3a）を持つときだけ、呼び手をその会話にする。版が許可外なら unsupported_version。名乗り（環境変数 `GROK_SESSION_ID` や引数の会話 ID）は使わない。祖先に Grok があって条件を満たさないとき（画面なしの `grok -p` を含む）は、さらに上の祖先を探さず caller_unobserved にする（Grok の中から呼ばれたものを別の会話の呼び出しと取り違えないため）。祖先が Grok かどうかは、台帳の pid に加えて、ps の名前が `grok`（実測 2026-10-08）の祖先は必ず実行ファイルを lsof で確かめて判定する。名前が `grok` の祖先で、実行ファイルが取れないとき、既知の場所（`~/.grok/bin/grok` と `~/.grok/downloads/grok-<版>-macos-*`）の Grok でないときも、そこで止めて caller_unobserved（grok_identity_unobserved）にする。別の場所に入れた Grok や、たまたま grok という名前の別の道具の中から呼ばれた場合も止まる（取り違えより「確かめられない」を選ぶ。変えるなら本人判断）。

段の後退と失敗
- 一度見えた段は戻さない（既存のとおり）。受信箱の封筒が壊れていれば配達せず、受理のまま「未確認」にする。

## P2 Grok Bot の作り

名簿（新規。外の実行主体の名簿 `~/.seamless/peers.json`、本人だけが書く、mode 0600、所有者が本人。Grok の台帳とは別）
- 外の実行主体の宛先の特定は spec.md の「段の言葉の定義」の節の末尾のとおり（製品 = grok-bot、ホスト = 外、会話 = 登録名、実行主体 = 鍵の版。ここでは参照だけ）。署名の対象の「宛先」もその形で書く。
- 1 件 = 登録名、表示名、製品（`grok-bot`）、宛先の住所を入れた環境変数の名前（Mac → Bot。webhook の URL）、送信鍵を入れた環境変数の名前（Mac → Bot の署名用。住所と別）、受信鍵を入れた環境変数の名前（Bot → Mac の検証用。送信鍵と別）、鍵の版、失効（`revoked` と日付）、許す操作（read は常に不可、send の可否。既定は不可で、本人が `send: true` と書いたときだけ送れる。一覧には read 不可と出す）、範囲（作業場所の一覧か、本人が明示したときだけ「すべて」。既定は無く、未設定は拒否。D6）。
- 名簿には環境変数の「名前」だけを書き、値は書かない。seamless は送る瞬間と受ける瞬間にだけ値を読み、記録に書かない。
- 信頼の境界: 名簿を書けるのは本人だけ、という前提は limits.json と同じ（同じ利用者の権限で動くプロセスは書ける）。seamless は mode と所有者が合わない名簿を使わず、操作のたびに読み直し（キャッシュしない）、配送の直前に失効を確かめ直す。

送る（Mac → Bot）
- 前提の gate: T0-4b（Q3 の答え。「未公開」なら上の保守的な既定を採る）が evidence.md に載るまで、送る経路の実装（T2-2）に入らない。T0-6（Bot → Mac の経路）は受ける経路（T2-3）の gate。
- 封筒を webhook の住所へ POST する。本文は封筒の JSON、ヘッダに送信鍵による HMAC-SHA256 の署名（対象は封筒の本文の SHA-256、送信時刻、nonce）を付け、茶々丸の側で送り手を確かめられるようにする（送信鍵の使い道。受信鍵とは別）。受理は HTTP の応答で記録する（2xx 以外は「受理されなかった」）。配信確認、処理開始、返答完了は観測できないので未確認のまま。返答完了だけは、Bot からの返信が届いた時点で埋まる。
- Q3 が「未公開」のときの保守的な既定: 1 回の POST に 1 封筒、本文 8,000 字まで（超えたら text_too_long）、2xx 以外は不受理、順序を仮定しない、再送しない。T2-2 の試験で、応答の順序、再送、上限の挙動に依存していない（応答が順不同でも、再送が無くても、結果が変わらない）ことを確かめる。
- 再送しない: 既存の予約（送る前に依頼の hash を claim する仕組み）に乗せる。同じ依頼 ID はもちろん、送り手、宛先、replyTo、本文が同じ依頼は別 ID でも duplicate になる。応答が切れたら「成否不明」で止め、実行回数は 1 のまま。
- 外部送信の承認: Mac の会話の文をクラウドの Bot へ送るのは外部送信に当たる。契約の事前承認（seamless で本人の別の会話へ送る）に茶々丸が入るかは、T2-8 の前に立花さんが決める（H7）。

受ける（Bot → Mac）
- 署名する場所は Bot の側（VPS。鍵の写しは本人が置く）。Bot は封筒に署名してから、Mac で seamless の CLI を実行する。署名済みの封筒は標準入力か一時ファイルで渡し、鍵も封筒も引数に書かない（会話と実行記録に残さないため）。Mac の seamless は環境変数の受信鍵で検証するだけで、Mac の鍵で任意の文に署名する入口は作らない。
- 署名（HMAC-SHA256）の対象は正規化した次の並び: 送り手の登録名、鍵の版、宛先（Mac 内の会話なら製品:会話 ID:世代。外の実行主体なら製品:登録名:鍵の版）、依頼 ID、replyTo（無ければ空）、本文の SHA-256、署名時刻（UTC、秒）、nonce。どれか 1 つでも違えば拒否。
- 時刻と nonce: 署名時刻は Mac の時計から ±5 分の内側だけ受け、未来も過去もそれより外は拒否。nonce は 24 時間（有効期限より長い）保存し、記録は原子的（claim と同じ `wx` のファイル作成）に行うので、同時に届いた 2 件は 1 件だけ通る。再起動後も記録はディスクにある。
- 拒否する 5 種（AC5）: 鍵なし、別の登録の鍵、失効した鍵、同じ nonce の再提示、宛先の登録の差し替え（署名した宛先と実際の宛先が違う）。送信鍵（Mac → Bot）で署名した封筒を受信鍵で検証しても通らないこと（2 つの鍵の取り違え）も拒否として試験する。名簿に無い登録名（未登録の送り手）も拒否する（spec.md の「分類の基準」の「未登録なら Mac 内の経路としても拒否」）。範囲外の宛先は AC8 の認可の拒否として別に扱う。
- 認可（AC8）: `--as` の経路は、名簿の登録の範囲と既存の制限の設定の交差で判定し、「制限の設定が無ければ許す」という既定に外の登録を合流させない。名指しの宛先でも範囲を再検証する。範囲が未設定、名簿が壊れている、範囲外、のどれでも一覧、読む、送るを拒否する。
- 届いた文は受信側の AI が自分の権限で判断する（不変条件 3）。seamless は承認設定も sandbox も触らない。
- Bot 側の応答が切れたとき（Bot → Mac の配送後に CLI の応答が Bot に届かない）: Mac の側は予約の仕組みで実行済みを覚えているので、Bot が同じ依頼を再実行しても duplicate で止まる。Bot が別 ID で同じ内容を再実行しても、内容の hash で duplicate になる（AC7。試験は T2-3 に含める）。

返信の対応と循環（AC6）
- 返信は `replyTo` で元の依頼に結び付ける。既存の検証（replyTo が実在する依頼を指し、返信者がその依頼の宛先であること。違えば `invalid_reply`）を外の送り手にも適用する。
- `replyTo` の無い文（Bot 間の転送で落ちた場合を含む）は新しい依頼として受けるが、seamless が自動で返信を送ることは無い（返信は AI が自分で `send` する）。
- 循環の検証は、未知の replyTo、重複、転送（replyTo なし）、返信の受信後 10 分（試験の時計）で依頼の件数が同じ、を注入する自動試験と、実会話で返信の受信後 10 分、依頼の件数が増えないことの実測（AC6 の「相手ごと」。Grok CLI は T1-6 と T1-10f、Bot は T2-5 と T2-8e、Claude⇄Codex は TC-4）。

## 検証

- 自動試験: `bash scripts/verify.sh`（型検査、node の試験、plugin の検証と試験）。新しい試験は既存の型（caller-scan、adapters、automatic、status）に足す。
- 実会話: 8 本の組 × 方向を evidence.md に時刻と段つきで記録。製品の版（Claude Code、Codex Desktop、Grok CLI の版）を各記録に添える（Done when に含める）。
- 判定: 工程ごとに、作った側と逆の家系の判定役（読み取り専用）。作る側がこの会話のリーダー（Claude）なら Codex Astra、作る側が Codex なら Claude Opus 5.5。敵対は判定役が判定のあとに兼ねる。
- 完了の宣言は、試験のコマンドの終了コードと判定役の PASS がそろったときだけ。

## 置いた仮定

- Grok の Stop hook の `additionalContext` は、相手の AI にとって「届いた文」として読まれる（hook feedback の扱い）。P0 で実測して確かめる。
- `active_sessions.json` は TUI の開始と終了で更新される（バイナリの文言から。P0 で実測）。
- Grok Bot の webhook は 1 回の POST に 1 封筒で、応答は HTTP の状態で足りる（Q3 で確かめる。確かめるまで T2-2 に入らない）。
- 茶々丸が Mac で実行する CLI は、立花さんの承認を 1 コマンドずつ受ける（ハンドオフ 5）。seamless はその承認の仕組みに手を入れない。
