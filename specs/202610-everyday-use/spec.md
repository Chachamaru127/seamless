## 何を、なぜ

既存ペアの5操作（探す、許可確認、読む、届ける、返事を受け取る）は、2026-10-02 に実会話で検収した。
ただし今は、AI がコマンドを打ち、手作りの名簿ファイルを使って動かしている。
立花さんが新しい会話で「Claude に聞いて」と言うだけでは、まだ使えない。

この機能は、検収済みの5操作を、普段の会話から言葉だけで使える状態にする。
ルートの spec.md の不変条件 1〜8 は変えない。

## 今日の実測で分かった弱点

| 観点 | 実測した弱点 |
|---|---|
| 導入 | 名簿ファイルを手で作る。会話 ID、世代、許可を人か AI が書く |
| 使い勝手 | 普段の画面に3つの道具が入っていない。AI がコマンド名と名簿の場所を知らないと使えない |
| 更新への強さ | Desktop が会話を再開すると Claude の会話 ID が変わり、名簿が古くなって送信が止まった（[観測記録](observations.md)）。Codex Desktop の版更新では、対応版の一覧を手で足した |
| 対応製品 | 実証は Codex Desktop 26.928.40906 と Claude Code 2.1.284（Desktop 同梱）のペアだけ。複数会話、別 worktree、Codex の busy 中の非中断は未実証 |
| 状態表示 | 送信は `submitted` までしか返さない。相手が読んだか、返事が来たかは、AI が相手の会話を読み直して確かめている。`invalid_reply` や `caller_unobserved` が、人に分かる理由になっていない |
| 実績 | 検収は1ペア、1日分。日をまたいだ利用、再起動後、版更新後の実績がない |

## 用語

- 自動でつなぐ: このMacで動いている Codex と Claude の会話を、名簿なしで相手として一覧にし、読む、送るを初めから許す（2026-10-03 立花さん決定。ルート spec の不変条件 8 を改訂）。
- 制限の設定: 立花さんが任意で置く設定。除外する会話、探す範囲、操作（read / send）の制限を書く。置かなければ制限なし。
- 呼ぶ側: 今 claudex の道具を呼んでいる会話。claudex が実観測で特定する。名乗りや引数の値では決めない。
- 探す範囲: 同じ作業場所（current_work）、同じリポジトリ（same_repository）、すべて（any）。既定は同じ作業場所。同じ作業場所は、呼ぶ側のフォルダと同じか、その中のフォルダ（親のフォルダや git の worktree 全体ではない。2026-10-03 実測で、親リポジトリの中にあるプロジェクトでは worktree 全体が広すぎたため）。
- 対応の組: 製品、完全な版番号、接続方式（Desktop / CLI）、通信の取決めの版の4つの組。
- 段階: 受理（窓口が受け付け、相手への書込みが成功）、到達（相手の記録に入ったことを読んで確認）、処理開始（相手がその依頼の処理を始めた記録）、返答完了（replyTo が一致する返事を読んで確認）、不明。既存の配送状態との対応は、受理 = accepted / submitted、到達 = observed、返答完了 = replied、不明 = unknown。処理開始は既存に対応がなく、今回新しく観測する。
- 常駐の見張り: アプリと無関係に動き続けるプロセス。アプリの接続中だけ動き、接続が切れたら終わるプロセスは含まない。

## 受け入れ条件（AC）

各 AC は Yes か No で判定する。各 AC の検証方法は Plans.md で試験名か実測手順に割り当てる。

### 導入
- AC1: 名簿も設定も置かずに、このMacで動いている Codex と Claude の会話が、呼ぶ側の探す範囲の中で一覧に出る。製品の組は問わない（Codex↔Claude、Claude↔Claude、Codex↔Codex）。
- AC2: 一覧を作るために会話の本文を取得しない（受け取ってから捨てる経路も不可）。使うのは識別情報（製品、会話 ID、世代、作業場所、稼働状態）だけ。本文に触れない取得経路を実証できない製品は、作業場所を「未確認」として一覧に出す。
- AC3: 呼ぶ側を実観測で特定する。特定できないときは、一覧、読む、送るのすべてを止め、理由を返す。道具の引数や相手の文で呼ぶ側を変えられない。
- AC4: 制限の設定を、4つ目の道具と、同じ内容のコマンドで、追加、変更、削除できる。設定を消せば制限のない状態に戻る。設定ファイルが壊れている、読めないときは、制限なしへ変換せず、一覧、読む、送るを止める。誰が道具を呼ぶかの運用は利用者に任せ、製品は道具の呼出しを本人の指示とも相手の文とも区別しない（AC28 の製品内の保証とは別）。
- AC5: 制限の設定に書いた除外と範囲が、一覧、読む、送る、照会のすべてに効く。
- AC6: 道具（3道具と制限の道具）を普段の画面へ入れる操作と外す操作が、それぞれ立花さんの1回の指示で終わる。外す手順は claudex が足した項目だけを消す。導入後に立花さんや他製品が同じ項目を変えていたら、上書きせず止める。

### 使い勝手
- AC7: 導入後に両アプリで新しい会話を始め、何も設定せずに「同じ作業場所の相手に確認して」の一言から、探す、読む、送るへ進める。
- AC8: Codex 側と Claude 側の両方から、探す、読む、送る、返事の照合までが、立花さんのコピー貼付けなしで終わる。終わりの判定は、返事を受け取り、replyTo が送った依頼 ID と一致したとき。
- AC9: 同じ条件で候補が2件以上あるときは止まり、選択肢を示す。探す範囲を AI の判断で自動で広げた回数が0（広げるのは道具の引数で明示したときだけ）。
- AC10: 返事を待つ上限と照会の間隔は Open decision 6 の値を使う。上限を過ぎたら「待機を終えた（相手の処理は取り消していない）」と示す。無返信と途中切断を試験する。
- AC11: 送信が止まったとき、結果に理由の種類を返す。種類は `caller_unobserved`、`invalid_reply`、未確認の対応の組、相手停止、待機上限の5つすべて。AI はその種類を、理由と次の一手を含む日本語の短い説明（句点1つまで）に直して示す。
- AC12: 送信が「不明」になったあと、同じ依頼を新しい ID で自動送信した回数が0。切断後の会話の流れを試し、相手の記録への書込み回数が増えないことを確かめる。

### 更新への強さ
- AC13: 相手の会話が再開や再起動で「世代だけ変わった」のか「会話 ID ごと変わった」のかを、一覧で区別して表示する。
- AC14: 世代や会話 ID が変わっても、名簿の書き直しなしで、新しい世代と ID の会話に読む、送るができる。
- AC15: 制限の設定で除外した会話は、会話 ID が変わっても除外が続くか、続かない場合は一覧で「除外が切れた」と分かる（どちらにするかは Open decision 2）。
- AC16: 一覧で選んだ宛先の会話 ID、世代、作業場所を固定して送信に渡す。送る直前に再照合し、選んだ時点と違えば止める。送信の時点で宛先を選び直さない。
- AC17: 古い世代、再利用された PID への書込みが0。古い依頼 ID の再送が0。
- AC18: 通常の read / send は、対応の組が対応表にあり、状態が「確認済み」のときだけ許す。表にない、確認中、修正待ち、未知の状態では止め、組と理由を示す。
- AC19: 新しい対応の組の確認は、立花さんが指定した試験用ペアだけで動く経路で行う。試験の合格だけでは通常利用の対応表へ自動で足さない。足すのは立花さんの確認の後。
- AC20: 「更新しても壊れない」とは表示しない。対応表の各組に状態（確認済み / 確認中 / 修正待ち）を持たせ、試験で不合格になった組は「修正待ち」にする。

### 対応製品
- AC21: 対応表に、対応の組、確認日、確認項目、状態（AC20）を載せる。載っていない組は「未確認」と表示し、AC18 で止める。
- AC22: 同じ2製品で、複数の会話、別 branch、別 worktree を実際の Git 作業場所で試し、誤送信が0。
- AC23: 相手が作業中（busy）に依頼を受けても、元の処理が中断されないことを両方向で確かめる。判定は、受信前から動いている処理の識別子に取消の記録がなく、その処理が最後まで完了したこと。

### 状態表示
- AC24: 送った依頼ごとに、段階（受理、到達、処理開始、返答完了、不明）を区別して照会できる。観測していない段階は「未確認」と出し、段階ごとに根拠と観測時刻を返す。依頼と対応付けられない処理単位の完了を、返答完了の根拠にしない。
- AC25: 照会は本文を返さず、ID、相手、世代、時刻、段階だけを返す。照会できるのは、その依頼を送った呼ぶ側だけ。制限の設定で read を止めた相手の記録は読み直さず、「未確認」を返す。他者の ID には、存在するかどうかも分からない応答を返す。
- AC26: 書込み後に切断したら「不明」と出る。同じ ID の再呼出しを新しい配送と表示しない。
- AC27: 一覧で、各相手の稼働状態（稼働中 / 停止 / 不明）と理由の種類（プロセス終了、世代変更、未確認の対応の組、通信不可）を出す。

### 安全
- AC28: 相手の会話から来た文を、立花さんの承認として扱わない。claudex のコード自身は、相手の文を理由に制限の設定、承認待ち、共通設定を変えない（製品内の保証。単体試験で確かめる）。受け取った AI が設定の道具を呼ぶかどうかは運用の範囲で、実会話の試験は製品の保証ではなく観測として記録する。制限の解除、承認待ちの解除、共通設定の変更を求める固定の試験文を、直接の受信、履歴の read、要約の経由の3つで試し、許可、承認待ち、設定が変わらないことを確かめる。
- AC34: 受け取った依頼の送り主を、送り主の会話の記録に同じ依頼 ID の送信があるかを読んで照合する。照合できたものだけ「確認済みの送り主」と表示し、できないものは「名乗った送り主」と表示する。帯の既読の色は確認済みの相手にだけ使う。
- AC29: claudex が管理する保存先と、保存してよい項目を一覧にする。元製品の正本とは区別する。通常時と失敗時のログ、標準エラー、試験の証拠に、検査用の文字列（本文、思考、認証値の代わり）が残らない。

### 実績
- AC30: 検証セットの各ケース（何も設定しない初回、制限の設定あり、会話の再開、版更新、複数ペア、同じ製品の組、busy 中の受信、無返信、途中切断、日をまたいだ利用、両アプリの再起動後）を、Open decision 3 で決めた件数だけ実施し、各試行について AC31a〜AC31c の証拠を記録する。
- AC31a: 送信前に拒否された試行は、拒否理由と、相手の記録への書込み0回を記録する。
- AC31b: 返事まで成功した試行は、元の ID、世代、乱数、replyTo、版、ソースの hash を記録する。
- AC31c: 観測できなかった項目は、項目名と理由を記録する。値を作らない。
- AC32: 試行、実配送、照合済みの返信、失敗、欠測を分けて数える。日数ではなく操作の回数で数える。
- AC33: 別家系の判定役が検証セットを判定する。

## Stop conditions

- 両アプリの共通設定への書込みは、Plans.md の Human gates で、書き込む設定、変更する項目、操作（導入、更新、修復、取り外し）ごとに承認を取るまで行わない。導入の承認を、更新や修復へ流用しない。配送は CJ-Plugin の wire 経路だけを使う。
- 常駐の見張りが必要になったら止める（Open decision 2）。
- 本文、思考、認証値を中継の記録へ保存する設計が必要になったら止める。
- 呼ぶ側を実観測で特定できない製品があれば、その製品からの呼出しは止める（AC3）。名乗りで代える設計にしない。
- 共有の受信箱、耐久配送キュー、自動再送が必要になったら止める。
- 別 Mac、クラウド会話、外部公開が必要になったら止める。他製品は Open decision 4 で決める。

## 決定事項

2026-10-02（承認1回目）
1. 道具を両アプリの普段の画面へ常設する。経路は CJ-Plugin の wire.sh。
2. 常駐の見張りは置かない。照会のたびに相手の記録を読み直す。
3. 検証セットは各ケース1回以上、両方向を含めて合計10往復以上。日をまたいだ利用と両アプリの再起動後を含める。
4. 他社製品（Cursor、Grok など）と CLI 単体の会話は今回の範囲から外す。
6. 返事を待つ上限10分、照会の間隔30秒。

2026-10-03
7. 名簿による登録をやめ、このMacの会話を自動でつなぐ。制限は任意の設定で行う。
8. 既定の探す範囲は同じ作業場所。
9. 4つ目の道具は制限の設定を扱う。
10. 同じ製品の組（Claude↔Claude、Codex↔Codex）を範囲に入れる。
（旧5「探索仕様との優先」は、登録をやめたため対象外）
11. Codex を呼ぶ側とする経路は道具（MCP）だけ。コマンド経由（`CODEX_THREAD_ID`）は持たない（T1b の実測による）。
12. 名簿からの移行は、名簿の中身にかかわらず「除外なし、同じ作業場所、操作の制限なし」の案を出す。名簿より許可が広がる点（名簿になかった相手、片方向や一部の操作だけの許可）は注意書きで知らせる。
13. 制限の設定ファイルが壊れていても、全消去（clear）だけは通し、制限なしへ戻せる。

## agmsg との関係

- 取り入れる: 初回設定の短さ、言葉だけの導線、診断と更新の手順。
