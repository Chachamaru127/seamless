## 何を

Claude と Codex の会話の間でできている「一覧、読む、送る、返信、段の観測」を、3 つの相手にも広げる。優先順は Grok CLI → Grok Bot → ChatGPT Dot。

| 相手 | 正体 | この Mac で実観測できるか | 送り手になれるか |
|---|---|---|---|
| Grok CLI | ターミナルの会話（Grok Build CLI） | できる見込み（会話の記録、稼働中の名簿、hooks が手元にある） | できる見込み（会話のプロセスが手元にある） |
| Grok Bot | クラウドで動く Bot（この Mac にプロセスは無い） | できない。入口は webhook の受け口だけ | 本人が名簿に登録し鍵で確かめる形でだけ |
| ChatGPT Dot | 未確認（本人が確認中） | 未確認 | 未確認 |

## なぜ

立花さんが会話を切り替えて文章を貼り直す手間をなくす、という seamless の目的を、Claude と Codex の 2 製品で閉じない。Grok CLI は日常の作業に入っている。Grok Bot は見回りと相談の相手で、Codex や Claude から直接話しかけたい（ハンドオフの依頼）。

## 製品の不変条件への影響（ルートの spec.md）

不変条件 1〜7 は維持する。8 を改訂する。

- 旧 8: 対象は同じ Mac で動いている Codex と Claude の会話とする。名簿による登録は求めず、相手は自動で見つける。
- 新 8（案）: 対象は、同じ Mac で実観測できる会話（Claude、Codex、Grok CLI）と、本人が名簿に登録した外の実行主体（Grok Bot、ChatGPT Dot）。Mac 内の会話は名簿なしで自動で見つける。外の実行主体は名簿と鍵で確かめ、名乗りだけでは送り手にも宛先にもしない。読む、送るの制限は本人が任意で置く設定で行う。既定の探す範囲は同じ作業場所（外の実行主体には作業場所が無いので、名簿の登録ごとに本人が範囲を決める）。

分類の基準（新 8 の「Mac 内」と「外」の線引き）
- Mac 内の会話: seamless が、その会話を持つプロセスを実観測で特定できるもの（Claude の会話の記録とソケット、Codex Desktop の窓口、Grok CLI の会話のプロセス）。
- 外の実行主体: それ以外のすべて。Grok Bot が Mac で実行するコマンドも「外」に入れる。名簿に登録され鍵で確かめられた場合にだけ送り手になり、未登録なら Mac 内の経路としても拒否する。登録名を引数で指定すること自体は名乗りではなく、鍵で確かめられた登録名の指定として扱う。鍵の無い名乗りだけでは代えない。

不変条件 3（seamless は配線だけ）と 4（受理、配信確認、処理開始、返答完了を別に記録。観測できない段階は未確認のまま）は、Grok Bot で特に効く。webhook は受理しか分からない。

段の言葉の定義（この spec で共通）
- 受理: 送り先が依頼を受け付けたと応答した（webhook の応答、ソケットの書込み完了）。Grok CLI には応答する口が無いので、seamless が受信箱に封筒を書き終えた時点を受理とする（相手の実行主体に渡す前の、seamless 側の受付）。
- 配信確認（届いた）: 相手の会話の記録に、その依頼 ID の封筒が現れた。Grok CLI では、hook が文脈に足した受領記録（依頼 ID、会話 ID、世代、時刻）と、相手の記録の同じ時刻以降の hook_execution（Stop、completed）の両方がそろった時点。
- 処理開始（読んだ）: 相手の会話の記録に、その依頼の後の相手の発話か道具の呼び出しが現れた。
- 返答完了（返信）: 元の依頼 ID を返信先に持つ封筒が、こちらに届いた。
- 各段は、依頼 ID、観測元、観測時刻を結び付けて記録する。無関係な発話や返信をその依頼の段にしない。
- 外の実行主体の宛先（不変条件 1 の「製品、ホスト、会話、実行主体」）: 製品 = 名簿の製品（grok-bot）、ホスト = 外、会話 = 名簿の登録名、実行主体 = 鍵の版。会話 ID と世代の代わりに登録名と鍵の版で特定する。

## 確認済みの事実と未確認（2026-10-08）

Grok CLI（1.0.46、手元で確認）
- 会話は作業場所ごとの保存先に、会話 ID 単位で保存される。要約（題、モデル、作成と更新の時刻）、会話の更新の流れ（発話と道具の呼び出し）、モデルに送った生の履歴、が別ファイル。
- 稼働中の会話の台帳がある（今は空。ロックつき。外の実行主体の「名簿」とは別）。項目名と更新のタイミングは未確認。
- hooks がある（会話の開始、発話の送信、停止、道具の前後）。hook の出力を会話の文脈に足せるかは未確認。
- 動いている TUI の会話に外から文を入れる正式な口は無い（Grok Build CLI 4.7 の回答、確信度 high。文書と、leader のソケットが今無いことから）。ACP は自分で起こした会話にだけ送れる。`grok -p -r <id>` は同じ会話を別プロセスで再開する（不変条件 2 に当たるので宛先にしない）。
- hooks の `Stop`（1 手の終わり）は、JSON の additionalContext で最大 10,000 字を文脈に足せる（hook feedback として、同じ手の次の round に入る）。`UserPromptSubmit` の標準出力は捨てられる（足せない）。会話の終了時の Stop は無視される。
- 稼働中の会話の台帳 `active_sessions.json` は、TUI が開始時に登録、終了時に削除する内部の台帳で、項目は会話 ID、pid、作業場所、開始時刻（確信度 medium。バイナリの文言から。公開文書には無い。画面なし `grok -p` は登録しない）。
- 会話の可視の発話と道具の呼び出しの正本は updates.jsonl（1 行が時刻、method、params。発話はチャンクで連結する）。chat_history.jsonl はモデルに送る生の履歴で、system_reminder などモデルにだけ渡る行を含む。
- leader（複数の会話をまとめる仕組み）は既定で切で、設定の reload と MCP の見張り用。
- seamless 側: Grok CLI の会話は製品の種類として未定義。呼び手の特定も Claude の祖先か Codex の metadata だけ。

Grok Bot（茶々丸の確認、seamless 側で検証できたものに印）
- 外から会話へ直接入る入口は無い。入口は webhook で動くルーチン（URL と鍵は本人がアプリからコピーし、Bot は鍵を見ない）。
- 起きた Bot はほかの Bot へ渡せる。本人への通知は判断が要るときだけにできる。
- 届く中身の大きさの上限、再送、順序、配送の確認は未公開 → 未確認のまま扱う。
- 逆向き（Bot → Mac）: Bot が Mac でコマンドを 1 つずつ本人の承認を受けて実行できる。✔ seamless 側で確認: 今の呼び手の特定は Claude の祖先か Codex の metadata を求めるので、Bot の Mac コマンドは `caller_unobserved`（native_ancestor_missing）になる。名乗りの引数で代える設計にしない方針は変えない。
- 受け口の Bot は茶々丸（D1 で決定）。

ChatGPT Dot（Codex の調査、立花さんが 2026-10-08 に貼り付け。全文は `.local/grok-consult/dot-research-2026-10-08.md`）
- Dot（ChatGPT の個人用の常駐エージェント）へは、ChatGPT の Tunnel（クラウドから Mac の MCP サーバーへ stdio を運ぶ仕組み）に seamless の MCP を載せると、起動とツール一覧までは通る（隔離試験で確認）。
- しかし Dot が自分から動き出す（seamless からの送信で応答を始める）には、MCP Events（MCP の新しい仕様 2026-07-28 にあるイベントの発見・購読・callback の仕組み）への対応が要る。今の seamless は 2025-06-18 の仕様で、`events/list` は unknown_method。購読の保持、ChatGPT の callback の安全な保持、署名つきのイベント配送、ローカルの送信をイベントへ変える入口、のすべてが未実装。
- 逆向き（Dot → Mac の会話）には、Dot を表す宛先と、Tunnel 越しの呼び手の認証が要る。今の呼び手の特定（ローカルの祖先プロセス）では Tunnel の遠隔の呼び手は `caller_unobserved` になる。→ 新 8 の「外の実行主体を名簿と鍵で確かめる」に乗せる（署名の secret が鍵に当たる）。
- 未確認: Tunnel の実際の接続状態、Dot 側の購読とイベント受信、MCP Events の一次仕様（発見、購読、callback、署名の正確な形）。

## 受け入れ条件（AC）

実証の単位は「製品の組 × 方向」。Claude→Grok CLI、Codex→Grok CLI、Grok CLI→Claude、Grok CLI→Codex、Claude→Grok Bot、Codex→Grok Bot、Grok Bot→Claude、Grok Bot→Codex の 8 本を、それぞれ 1 回以上。製品の版（Desktop か CLI か）を記録に残す。

| # | 条件 | 検証（Yes か No で判定できる観測） |
|---|---|---|
| AC1 | Grok CLI の会話が一覧に出る。製品、ホスト、会話、実行主体（動いている／止まっている）を区別して示す | 一覧に Grok CLI の会話が製品名と状態つきで出る。止まっている会話が「動いている」と出ない |
| AC2 | Claude か Codex の会話から Grok CLI の会話へ送ると、受理、配信確認、処理開始、返答完了の 4 段を観測できる。観測できない段は未確認のまま出す。届けるのは送信前から存在したその会話の実行主体で、同じ履歴を別プロセスで開いた相手を成功扱いにしない | 送信前後で会話 ID と実行主体の世代が一致した往復が 2 方向で各 1 回。別プロセスで同じ履歴を開かせる否定試験で「届いた」が立たない |
| AC3 | Grok CLI の会話から Claude か Codex の会話へ送れる。呼び手は実観測で特定し、名乗りでは通さない | 2 方向で各 1 回の往復。名乗りだけの呼び出しが `caller_unobserved` になる自動試験 |
| AC4 | Claude か Codex の会話から Grok Bot へ送ると、受理（webhook の応答）、配信確認、処理開始、返答完了を独立した 4 項目として記録する。観測できない段は未確認のまま出す | 2 方向で各 1 回の送信。受理だけ観測で残り 3 段が「未確認」と出る。後で返信が届いたら返答完了だけが埋まる |
| AC5 | Grok Bot から Claude か Codex の会話へ送れる。鍵は名簿の「送り手の登録」に結び付け、宛先の登録と対で確かめる。鍵なし、別の登録の鍵、失効した鍵、同じ署名の再提示、宛先の登録の差し替え（署名した宛先と実際の宛先が違う）を拒否する。webhook の送信鍵（Mac→Bot）と Bot→Mac の鍵は別物として扱う。鍵はリポジトリ、会話、記録に書かない | 2 方向で各 1 回の送信。5 種の拒否がそれぞれ自動試験で拒否される。記録とリポジトリに鍵の値が無い（grep） |
| AC6 | 返信は元の依頼 ID に対応づく。返信を受けた後に新しい依頼が自動で増えない（Bot がほかの Bot に渡しても、seamless の側で依頼が循環しない） | 相手ごとに、返信の受信後 10 分で依頼の件数が増えない自動試験と実測 |
| AC7 | 新しい経路（Grok の受信箱へ置く、webhook へ送る、署名済みの封筒を受ける、の 3 つ。Grok CLI から Claude や Codex へ送る経路は既存の配送経路を使うので既存の試験で守る）のそれぞれで、書込みの後に応答が失われても成否不明のまま保ち、同じ依頼（同じ ID、または別 ID で同じ内容）を自動で再実行しない | 経路ごとに、書込み後の切断を起こす自動試験で実行回数が 1 のまま |
| AC8 | 登録と鍵が通っても、範囲が未設定（Grok CLI では台帳の作業場所が読めない）、設定が壊れている、範囲外の会話を名指し、のどれでも一覧、読む、送るを拒否する。届いた文は受信側の承認設定や sandbox を変えない | 3 条件の拒否の自動試験。受信後に承認設定と sandbox の設定が変わっていない比較 |
| AC9 | Grok CLI の会話の可視の発話を読める（Claude、Codex と同じ操作）。Grok Bot は一覧と本文の読み取りに非対応で、その旨を操作の可否として示す | Grok CLI の読み取りの実測 1 回。Grok Bot の登録で read が不可と表示される |
| AC10 | 既存の Claude⇄Codex の往復と全自動試験が壊れない | 既存の検証一式が exit 0、実往復 1 回 |
| AC11 | ChatGPT Dot は、MCP Events の一次仕様を読んで AC（イベントの購読、署名つき配送、Dot の宛先と呼び手の鍵）をこの spec に追記し、別途の承認を得るまで実装しない。seamless の MCP の仕様の版の引き上げ（2025-06-18 → 2026-07-28）が Claude と Codex の接続を壊さないことを AC10 で守る | この spec の改訂と承認の記録。版の引き上げ後も AC10 が exit 0 |

## Stop conditions（止まる条件）

- 外の実行主体（Grok Bot、Dot）を名乗りだけで送り手にする設計、または鍵を送り手の登録に結び付けない設計になりそうなとき。
- 鍵や接続資格をリポジトリ、会話、記録に書く設計になりそうなとき。
- 届いた文で送信、削除、課金、マージ、本番反映をする設計、または接続のために受信側の sandbox や承認設定を緩める設計になりそうなとき。
- 成否が不明な送信を自動で再送する設計（別 ID で同じ内容を送る形を含む）になりそうなとき。
- 同じ履歴を別プロセスで開いて届けたことにする設計になりそうなとき（Grok CLI の ACP で新しい会話を起こす案はこれに当たる。採るなら「新しい会話として」別に承認する）。
- Grok CLI への届け方（D5）が未決のまま実装に入りそうなとき。
- Grok Bot の webhook の上限、順序、再送の挙動が分からないまま、それに依存する設計になりそうなとき。答えが「未公開」なら、依存しない保守的な既定（1 回の POST に 1 封筒、本文 8,000 字まで、2xx 以外は不受理、順序を仮定しない、再送しない）を Plans.md に書き、依存しないことを試験で確かめてから進む。
- Bot → Mac の入口として、待受サーバー、公開 URL、常駐処理、ネットワークへの口の公開、接続設定の変更が必要になったとき（「外部公開」はネットワークへ口を開くことを含む。製品の配布だけではない）。
- クラウドの会話どうしの通信が必要になったとき（今回解除するのは、名簿に登録した Bot と Mac の会話の間だけ）。

- D4 仮決め（2026-10-08、同上）: Dot はこの計画に残す（AC11 の形）。一次仕様を読むまで AC は置かない。

- D5 決定（2026-10-08 立花さん「推奨で」）: (a) と (b) の組み合わせ。以下は選択肢の記録。選択肢: (a) Stop hook で、相手の会話の次の 1 手の終わりに additionalContext として足す（動いている会話の実行主体に届く。相手が待機中の間は届かず「受理・未配信」のまま）。(b) 相手が待機中なら本人に知らせる（帯の通知）だけにする。(c) ACP か `-r` で別プロセスを起こして届ける（不変条件 2 に当たるので採らない）。推奨: (a) と (b) を組み合わせる。seamless 側は受理のあと、hook の受領記録と相手の記録の hook_execution がそろった時点を配信確認、相手の次の発話を処理開始とする（段の定義と同じ）。(b) の「帯で知らせる」は、配信確認が無い間は「未配信」と出し、相手の記録に 5 分以上動きが無いときだけ「相手は 5 分以上動いていない。次の 1 手の後に届く」と添える形。
